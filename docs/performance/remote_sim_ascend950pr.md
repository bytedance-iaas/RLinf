# 昇腾 950PR + GPU 远程仿真：LIBERO 与 ManiSkill 的 POC、配比与选型

本报告回答一个问题：π₀.₅ 在 950PR 上做 RL 时，把仿真放到 GPU 机器上能快多少，以及这台 950PR 该配什么型号、多少张仿真卡最划算。LIBERO 与 ManiSkill 各给一个结论：LIBERO 只缺 GPU 渲染，用「物理本地 + 渲染远程」；ManiSkill 缺整张 GPU（GPU PhysX），用「整 env 远程」。结论放在第 0 节，其余各节给出支撑它的测量；测量口径、本轮发现的问题与未完成项集中在第 10 节。

测量时间为 2026-10-31 至 11-02（L4 的 ManiSkill 在 11-02 补测），代码为 `feat/remote-sim-env`（基于 rebase 到上游 `d80cf00e` 之后的 `dev`）：渲染远程 `e99c2456`，整 env 远程 `e73a5f32`。

## 0. 结论

**LIBERO：物理留在 950PR、只把渲染放到 GPU 机。**

1. **单卡训练每步快 1.78 倍，两卡快 1.86 倍，评测快 27%。** 1 张 950PR、8 个 env、每步都渲染两路相机的 TC1 配置下，每步时间从本地 OSMesa 的 64.1 s 降到 36.0 s；两卡（每卡 8 env）从 67.3 s 降到 36.3 s，单卡吞吐保持 99%。节省的时间全部来自 env 段，NPU 上的 predict 与训练不变。每卡 env 加到 32 时远程每卡 69.1 env-step/s、本地 51.6（1.34 倍），远程只用 8 个 env 就超过本地 32 个 env 的吞吐。LIBERO-Spatial 500 局评测在远程渲染下 success_once 0.812（本地 0.840、TC1 0.822，在抽样误差内），rollout 从 776 s 降到 565 s。
2. **一张渲染卡就够整台 950PR（16 卡）；每步都渲染时选一张 4090 或 4090 D，开 `skip_intermediate_renders` 时选一张 L4。** 远程渲染后单卡吞吐在每卡约 32 个 env 时饱和（瓶颈回到 NPU），渲染需求封顶在每卡峰值约 205 帧/s，整机 16 卡约 3,300 帧/s；4090、4090 D、L20 单卡上限 6,500–7,100 帧/s，L4 4,300（12 核 CPU 先满，每步都渲染时余量小）。渲染卡几乎不干活（一帧 0.15–0.3 ms GPU 时间），限制服务端的是 CPU：每步都渲染时 ≥16 vCPU，开 `skip_intermediate_renders` 时 ≥8 vCPU。按火山引擎的价格系数（L20 为 1），4090 与 4090 D 是 0.756，L4 是 0.474；无论选哪种，摊到每张 950PR 都只有 L20 单价的 3–6%。
3. **LIBERO 不要整 env 远程。** 同为 1 卡、8 env、不录视频，整 env 远程每步 39.3 s，比渲染远程的 34.6 s 慢 13.6%（多出的时间主要是回合开始时的场景重建，搬到了 GPU 机共享的 CPU 上），GPU 机还要为每个 env 出一个 CPU 核。整 env 远程留给物理本身需要 GPU 的仿真器。

**ManiSkill：整个 env 放到 GPU 机，950PR 只做训推。**

4. **单卡吞吐是 H20 单卡的 2.4 倍，瓶颈在 NPU。** 每卡 40 env 时每步 128.5–130.7 s（4.9 样本/s/卡），H20 单卡（同卡跑仿真与训练）311.7 s（2.05 样本/s）。每步里训练 75 s、predict 22 s、env 40 s，其中网络只有 0.35 s。两卡各占一张 GPU 时单卡吞吐保持 97%。
5. **开 NVIDIA MPS 后，多张 950PR 可以几乎不掉速地共用一张仿真卡，限制变成显存。** 不开 MPS 时多个会话在 GPU 上分时执行，两卡共用一张 4090 每步慢 29%；开 MPS 后只慢 2.4%，三卡共用一张 L20 慢 10.8%。一个 40 env 的会话约占 8 GB，24 GB 的卡（4090、4090 D、L4）放得下 2 个，46 GB 的 L20 放得下 5 个。
6. **最佳配比：开 MPS 共卡；950PR 的单价不低于一张 L20 时选 4090 或 4090 D 的 2:1，低于时选 L20 的 4:1。** 仿真卡按火山引擎的价格系数（L20 为 1，4090 与 4090 D 0.756，L4 0.474）；950PR 的价格未给，记为 L20 的 x 倍。x > 1 时 4090 / 4090 D + MPS 的 2:1 每单位价格的样本/s 最高（实测，整机 16 张 950PR 配 8 张），x = 2 时比 L20 4:1 高 4%；x < 1 时 L20 + MPS 的 4:1、5:1 最高（外推，整机配 4 张），x = 0.5 时比 4090 2:1 高 6–9%；x = 1 时三者相差约 0.1%。950PR 越贵，越该选单会话快、共卡少的配法。L4 比 4090 便宜 37%，但单会话慢约 1/4，在任何 x 下都不是最好的（x = 1 时比最好的低 1.3%）。不能开 MPS 时只能 1:1，x < 2.4 时选 L4，否则选 4090 / 4090 D。第 7.2 节给出按 x 的表、各配法之间的分界点，以及「每卡 80 env、独占一张卡」这个改变训练设置的选项。

**两者共同**

7. **网络不是瓶颈。** 单条 TCP 流被限在 0.3–0.44 Gbit/s，两种模式都用多连接绕开：LIBERO 每个 env 子进程一条连接，每帧往返 5–7 ms；ManiSkill 每个会话 16 条数据连接并行，一个 40 env 的 chunk 回传 35 MiB 只用约 22–24 ms，约占 step 的 0.3%。
8. **更正**：上一版报告写的「物理卡 15」实际是物理卡 8（RLinf 的 placement 忽略了外部设的 `ASCEND_RT_VISIBLE_DEVICES`，见 10.1 节）；那几轮的时间数据不受影响，NPU 功耗数据作废。

## 1. 方案

950PR 没有图形栈，也没有 CUDA。LIBERO 的物理是 CPU 上的 MuJoCo，缺的只是 GPU 渲染：OSMesa 软渲染一对 256×256 相机画面约 100 ms、占近 2 个核，是一个动作 chunk 物理开销（5 步 × 7.2 ms）的近 3 倍。ManiSkill 的物理本身就是 GPU PhysX，950PR 上只能退回 CPU 物理，每个进程只能跑 1 个 env，而一张 GPU 能同时跑上百个。所以远程仿真层做了两种切法，共用一套编解码与传输：

| 模式 | 配置 | 切点 | 950PR 上跑什么 | GPU 机上跑什么 | 适用 |
|---|---|---|---|---|---|
| 渲染远程 | `env.<split>.remote_render.address` | robosuite 的离屏渲染上下文 | LIBERO 物理、观测、reset | 只做 `mjr_render` 与读回像素 | LIBERO（MuJoCo 系） |
| 整 env 远程 | `env.<split>.remote.address` | EnvWorker 构造 env 的那一行 | EnvWorker 只转发动作与观测 | 用 `get_env_cls` 构造的真实 env | ManiSkill、LIBERO |

### 1.1 渲染远程（LIBERO）

- 每个 LIBERO 子进程里，robosuite 的离屏渲染上下文被替换为远程替身。替身照常在本地跑 `mjv_updateScene`，把生成的 `mjvScene`（geom 列表、灯光、相机，一个 LIBERO 视角约 20 KB）发到渲染服务；服务端只做 `mjr_render` 与读回像素。
- 服务端按「可视签名」缓存渲染上下文：签名是 `mjr_makeContext` 读取的全部模型数据（网格、贴图、材质、高度场、plane geom、可视化选项）的哈希，不含物体位姿。LIBERO-Spatial 的 10 个任务、以及每次 reset 的重建共用一个签名，模型（约 260 MB 的 MJB）每个服务只上传一次。
- 每个子进程一条 TCP 连接。物理用 950PR 自己的 256 线程（纯物理实测 12,879 env-step/s，见 4.3 节），视频录制、数据采集、外部奖励模型等需要逐步观测的功能不受影响，GPU 机器上也不需要 LIBERO 资产。

### 1.2 整 env 远程（ManiSkill，以及 LIBERO 的对照臂）

- **切点**：EnvWorker 构造 env 处一个分支。`env_type` 仍写真实仿真器，远程是与它正交的配置块，所以 `prepare_actions()` 等按 `env_type` 的逻辑不受影响，950PR 上也不需要装仿真器。EnvWorker 放在忽略硬件的 CPU 节点组上，只做转发。
- **显式代理**：`RemoteEnv` 只实现 EnvWorker 调用的方法（`reset`、`chunk_step`、`step`、`update_reset_state_ids`、`is_start`、`close`），不用 `__getattr__` 通配转发；EnvWorker 用 `get_env_attr` 探测的可选能力因此读作「没有」，而不是变成远程调用。
- **只回最后一步**：EnvWorker 只读 chunk 最后一步的观测与 info（外部奖励模型、在线 LeRobot 除外），所以服务端只回最后一步，ManiSkill 的传输量降到 1/5。`validate_cfg` 拒绝与远程同时开启视频、数据采集、env offload、外部奖励模型与在线 LeRobot。
- **会话即进程**：服务端父进程只做 accept 与分发（启动时查一次 CUDA 与 EGL 设备的对应关系，不建 CUDA context），每个代理 spawn 一个子进程、按轮转绑一张 GPU（`CUDA_VISIBLE_DEVICES`，MuJoCo 系另设对应的 EGL 设备），断连即关 env、子进程退出，不留占卡的孤儿进程。
- **传输**：1 条控制连接 + K 条数据连接（默认 16），超过 1 MiB 的回复按连接数切成连续分段并行发送，接收端重组。两种模式都用 JSON 头 + 原始 buffer，不用 pickle。
- **一致性与可复现**：握手时比对两端 `rlinf/envs` 的代码哈希，不一致默认拒绝；服务端异常以 `RemoteError` 带原始 traceback 回到客户端，会话继续服务；服务端用代理从 EnvWorker（已播种）的 torch RNG 里取出的数给会话进程播种，`runner.deterministic` 同步生效（见 2.3 节）。
- **度量**：每次调用记往返与服务端耗时，按步汇总为 `time/env/env/remote_{round_trip,server,transfer}`，渲染远程对应 `remote_render_*`。`remote_transfer` = 往返 − 服务端，即网络加两端编解码，直接回答「网络是不是瓶颈」。

### 1.3 与 lerobot `d9902fe5` / `32b9993a` 的对照

先按上面的方向独立设计（草稿 v0），再对照 lerobot 的远程 env 实现。方向一致的部分：切点都在向量化 env 这一层；都用显式的调用白名单而不是通配转发；服务端都用框架自己的工厂构造 env。

| 方面 | lerobot | 本实现 | 原因 |
|---|---|---|---|
| 序列化 | pickle（声明「可信网络」） | JSON 头 + 原始 buffer，未知类型带 key 路径报错 | 仿真机是共享 VPC 机器，反序列化即可执行代码 |
| 传输 | gRPC + 分块字节流 | 原生 TCP，1 控制 + K 数据连接条带化 | gRPC 的 HTTP/2 单连接解决不了逐流限速（实测单流约 0.3 Gbit/s） |
| 服务端结构 | 单服务单 env 集 | 一会话一子进程，GPU 轮转 | 多张 950PR 共用一台仿真机；断连即释放 GPU |
| 回传内容 | 整个 step 的结果 | chunk 只回最后一步 | ManiSkill 每个子步都渲染，全量回传带宽 ×5 |
| 代码一致性 | 无 | `rlinf/envs` 代码哈希握手 | 两端代码不一致时行为会静默分叉 |
| 异常 | 还原成原类型 | `RemoteError` 带原始类型名与 traceback，会话继续服务 | 信息量相同，客户端不必导入服务端的异常类 |
| 可复现 | 未涉及 | 会话进程用客户端 RNG 播种 | 见 2.3 节 |

从 lerobot 采纳的经验：它的 4 个 bug 都是跑完整评测才暴露，所以除单测外必须用真实 EnvWorker 的训练与评测路径闭环（第 3、5 节）；静态元数据（`num_envs`、`seed`）在握手时一次取回，不逐次往返；服务端启动即打印绑定地址、GPU 分配与代码哈希。

## 2. 正确性

### 2.1 单测

`tests/unit_tests/test_remote_env.py` 共 19 个用例，在 950PR（OSMesa）与 4090（EGL）上都通过：编解码往返（含 bf16、嵌套容器）与未知类型报错、条带化、两种模式的配置校验、远程 env 与本地 env 结果一致（含只回最后一步）、异常过线后会话继续服务、代码哈希不一致被拒、断连后服务端进程退出、EnvWorker 按配置构造代理、会话播种，以及渲染远程与本地上下文的逐位比较。

### 2.2 LIBERO 渲染远程

- 两个用例把远程渲染的帧与同进程本地渲染的帧逐位比较，覆盖 RGB、深度、分割、阴影、雾，以及「同一上下文、不同模型 extent」的情况。
- **变异测试**：去掉逐帧的 extent 覆盖，远景帧有 30 个像素不同；去掉逐帧设置雾距离，带雾的帧有 15% 像素不同。两处都是读 MuJoCo 3.8.1 源码（`render_context.c`）后补上的：上下文在创建时把 `stat.extent` 烘进了阴影裁剪面、雾距离和无限大平面的网格，其中雾距离写在 GL 状态里，`mjr_render` 不会每帧重设。
- **LIBERO 逐任务对照**（4090，EGL）：LIBERO-Spatial 10 个任务，每个任务 41 步、两路相机，本地 EGL 与远程渲染的图像逐位一致，最终仿真状态逐位一致。唯一的例外是任务 2 第 38 步手腕相机有 3 个像素值差 1，三次里出现两次，且只在本地与远程 env 在同一进程里交错渲染时出现；分进程各跑 4 次时，远程彼此一致、也与本地一致，本地 6 次彼此一致。
- **期间修掉的问题**：可视签名漏了 plane geom（会让 plane 不同的场景错误共用上下文）；雾的 GL 状态；`SceneCodec` 用未初始化的 scene 内存推断字段类型（新分配的内存恰好是零时不出错，内存复用时会因 label 解码失败而崩溃）。

### 2.3 ManiSkill 整 env 远程，以及由此修掉的可复现问题

4090 上，40 个 env、同一组随机动作，本地 env 与经服务端（回环）的远程 env 逐字段比较观测、奖励、termination、truncation 与完整 info。第一版对照只跑了 12 个 chunk（60 步，小于回合上限 80 步），没有覆盖回合结束和自动 reset。补到 20 个 chunk 后：

- 本地两次运行在第 16 个 chunk（40 个 env 全部截断并自动 reset）之后就不一致：reset 时选的任务、物体从**进程全局 RNG** 取数。训练里 EnvWorker 在构造 env 前用 `actor.seed` 播种（`configure_determinism`），本地 env 因此可复现；而服务端的会话进程原先没有播种，远程训练不可复现。
- 修复：代理从 EnvWorker 的 torch RNG 取一个数随 `make` 请求发给服务端，会话进程据此 `seed_everything`，并同步 `runner.deterministic`。每个会话取到不同的数，各会话的随机流互不相同。
- 修复后（对照脚本的本地臂按同样方式播种）：本地两次 0/1236 个字段不同，远程对本地 0/1236，覆盖第 16 个 chunk 的截断与自动 reset。
- 新增单测 `test_remote_env_seeds_each_served_env_from_the_client_rng`；去掉服务端的 `seed_everything` 后该用例失败（变异验证）。

远程训练与本地训练因此在统计上一致、逐步不一致（两者取的随机流不同）。第 5 节的第一轮 ManiSkill 端到端（`ms_remote_1c_r1`）是修复前跑的，会话进程未播种，只影响可复现性，不影响统计行为。

## 3. LIBERO 端到端

### 3.1 单卡 POC

配置：TC1 的 `pi05_libero_1c`（每卡 8 env、gbs 64、micro 16、horizon 240，每步都渲染两路相机）加 TC1 armB_npu 的五个开关，物理卡 8（见 10.1 节），12 步取后 8 步。两臂只差 `++env.train.remote_render.address`；远程臂的渲染服务在 4090×8 的一张卡上（4 个 worker）。各跑 1 次。

| 指标（s） | 本地 OSMesa | 远程渲染 | 变化 |
|---|---:|---:|---:|
| time/step | 64.11 | 36.01 | −43.8% |
| generate_rollouts | 53.88 | 25.29 | −53.1% |
| env/env_interact_step | 35.23 | 11.02 | −68.7% |
| env/bootstrap_step | 9.28 | 5.01 | −46.0% |
| rollout/predict | 13.35 | 13.83 | +3.6% |
| actor_training | 8.81 | 9.21 | +4.5% |
| success_once | 0.484 | 0.453 | 每点 8 个 env，在抽样误差内 |

远程臂的 env 段仍有 11 s：240 步 × 约 46 ms/步，其中物理 7.2 ms、两路相机的往返约 10 ms，其余是 EnvWorker 自身的观测打包与进程间传输，和渲染无关。

### 3.2 每卡 env 数扩展（NPU 需求）

把每卡 env 数从 8 加到 16、32（global batch 等比放大，每个 rollout epoch 仍是 6 次更新），1 张卡（物理卡 8），其余同 3.1 节，远程与本地 OSMesa 各跑 1 次。

远程渲染：

| 每卡 env | step | rollout | predict | env_interact | bootstrap | actor | env-step/s/卡 | 帧/s/卡（平均） | 帧/s/卡（rollout 峰值） |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 36.0 | 25.3 | 13.8 | 11.0 | 5.0 | 9.2 | 53.3 | 107 | 152 |
| 16 | 59.8 | 40.4 | 25.2 | 14.5 | 9.0 | 18.0 | 64.2 | 128 | 190 |
| 32 | 111.1 | 74.9 | 50.2 | 20.5 | 17.3 | 34.6 | 69.1 | 138 | 205 |

本地 OSMesa：

| 每卡 env | step | rollout | predict | env_interact | bootstrap | actor | env-step/s/卡 | 远程 / 本地 |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | 64.1 | 53.9 | 13.3 | 35.2 | 9.3 | 8.8 | 29.9 | 1.78× |
| 16 | 98.5 | 79.7 | 25.4 | 46.2 | 17.1 | 17.4 | 39.0 | 1.65× |
| 32 | 148.8 | 111.5 | 49.8 | 47.4 | 32.8 | 35.6 | 51.6 | 1.34× |

（时间单位 s；帧数按每 env-step 两路相机计，即每步都渲染。）

- predict 与 actor 都随 env 数线性增长，单卡吞吐在约 69 env-step/s 饱和：远程渲染之后瓶颈已经回到 NPU。渲染需求随之饱和在每卡平均约 140、峰值约 205 帧/s。
- 打开 `skip_intermediate_renders`（chunk 5 时只渲最后一步；TC1 E1 在 500 局上测得成功率差 0.006，在抽样误差内），帧数降到 1/5。
- 本地 OSMesa 的 env 段在 16 和 32 env 时都是约 47 s：每个 env 一个子进程并行渲染，CPU 还没满（32 × 1.8 核 ≈ 58 核）。远程的 env 段从 11 s 涨到 20.5 s，原因是这组实验的服务端只开了 8 个 worker，32 个 env 同时请求时帧在 worker 上排队。按第 4.1 节 worker 数与往返延迟的关系，多开 worker 应能缩短这段排队，但没有在训练里验证。
- 本地对照的第一次 16 / 32 env 运行被误停过：在同一容器里跑单测时，`ray stop` 停掉了它们的 Ray 集群。上表是之后完整重跑的结果。
- bootstrap 随 env 数线性增长，原因与渲染无关：`ReconfigureSubprocEnv.reconfigure_env_fns` 逐个子进程发出重建请求并同步等待回复，32 个 env 的重建是串行的。改成先全部发出、再统一接收，32 env 时可省下约 15 s/步（约 14%）。

### 3.3 两卡

物理卡 14、15，每卡工作量不变（共 16 env、gbs 128），其余同 3.1 节；远程臂的渲染服务在 4090×8 的一张卡上（8 个 worker），16 个 LIBERO 进程共用。

| env/env_interact_step | 36.50 | 10.06 | −72.4% | 11.02 |
| env/bootstrap_step | 9.56 | 5.26 | −44.9% | 5.01 |
| rollout/predict | 14.42 | 14.17 | −1.7% | 13.83 |
| actor_training | 9.98 | 10.00 | +0.2% | 9.21 |
| env-step/s/卡 | 28.5 | 52.9 | 1.86× | 53.3 |

- **两卡时远程渲染的收益不变**（1.86 倍，1 卡 1.78 倍），单卡吞吐保持 99%（52.9 对 53.3 env-step/s）：16 个 LIBERO 进程共用一张渲染卡的 8 个 worker，没有出现排队。

### 3.4 整 env 远程对照臂

LIBERO 的物理也可以连同渲染一起放到 GPU 机上，即 ManiSkill 用的整 env 远程。代价是 GPU 机要替每个 env 出一个 CPU 核跑物理，好处是 950PR 上一个仿真进程都不用起。1 卡、8 env，物理卡 15；env 服务在 4090×8 的容器里（物理跑在 Xeon 8457C 上，EGL 在服务端本地渲染）。

整 env 远程不支持逐步观测的功能，第一次运行被 `validate_cfg` 拒绝：`env/libero_spatial.yaml` 在 train split 上默认就开着训练视频（`video_cfg.save_video: True`），3.1–3.3 节的运行其实都在录。所以这一组两臂都关掉训练视频，渲染远程臂在同一张卡上重跑：

| 指标（s） | 渲染远程 | 整 env 远程 | 变化 |
|---|---:|---:|---:|
| time/step | 34.59 | 39.30 | +13.6% |
| generate_rollouts | 24.04 | 28.45 | +18.4% |
| env/env_interact_step | 9.65 | 10.89 | +12.8% |
| env/bootstrap_step | 5.15 | 8.26 | +60.4% |

`evaluations/libero/libero_spatial_openpi_pi05_eval.yaml` 评 `RLinf-Pi05-LIBERO-SFT`：500 局 = 10 个任务 × 50 个固定初始状态，240 步，`auto_reset` 开，逐帧渲染两路相机并录视频；物理卡 14、15，每卡 250 个 env。两臂只差 `++env.eval.remote_render.address`；渲染服务在 4090×8 的 4 张卡上（16 个 worker）。

|---|---:|---:|---:|

| success_at_end | 0.668 | 0.690 | 0.678 |
| rollout 用时 | 776 s | 565 s（−27%） | — |

## 4. LIBERO 渲染供给

### 4.1 完整服务（含网络）：一张 4090

物理在 950PR，N 个 LIBERO 进程，每 chunk 5 步只渲染最后一步（每 env-step 0.4 帧），服务端一张 4090、W 个 worker。

| W | 64 进程：env-step/s（帧/s） | 128 进程：env-step/s（帧/s） | 128 进程每帧往返 |
|---:|---:|---:|---:|
| 2 | 2,144（858） | 2,120（848），已饱和 | 127 ms |
| 4 | 3,664（1,466） | 4,746（1,898） | 34 ms |
| 8 | 3,786（1,514） | 6,696（2,678），未饱和 | 12.6 ms |

对照：同样的 64 个进程本地 OSMesa 是 1,868 env-step/s，单进程 36.3 env-step/s；远程单进程 106.9 env-step/s（快 2.9 倍），每进程 CPU 从 1.72 核降到 0.79 核。

一个 worker 满载时每帧在 GL 线程上约 2.4 ms（轻载 1.3 ms），即约 400 帧/s；GPU 利用率在 20–40%。

L20 上的完整服务（16 个 worker），客户端放在 4090×8 的容器里（物理跑在 Xeon 8457C 上）：64 进程 2,975 env-step/s（1,190 帧/s，每帧往返 7.7 ms），128 进程 4,413 env-step/s（1,765 帧/s，往返 5.4 ms、服务端每帧 1.29 ms）。128 进程时服务端仍很轻松，限制来自客户端那台机器的 CPU（每进程 0.94 核，已满）。冷启动时 16 个 worker 里有 3–4 个各自要了一次模型（共约 1 GB）：同一 worker 内只上传一次，跨 worker 只靠磁盘缓存去重。

### 4.2 各型号卡的上限（不含网络）

用录下的真实 LIBERO scene 反复执行服务端的解包 + `mjr_render` + 读回，N 个进程各持一个 EGL 上下文，找饱和点。

| 卡（主机 vCPU） | 单进程帧/s | 饱和帧/s | 饱和时进程数 | 瓶颈 |
|---|---:|---:|---:|---|
| RTX 4090（4090×8，180） | 747 | 6,690 | 16 | GPU（SM 100%） |
| RTX 4090 D（22） | 611 | 7,090 | 16–20 | GPU（SM 98%） |
| L20（30，EPYC 9A75） | 939 | 6,500 | 8 | GPU（SM 100%） |
| L4（12） | 691 | 4,320 | 12 | CPU（解包从 1.0 涨到 2.0 ms） |

每帧时间的拆分（4090）：客户端打包 0.48 ms（950PR 上 0.28 ms），服务端解码 0.09 ms、解包 0.94 ms、渲染 + 读回 0.29 ms。也就是说服务端的成本大头是 Python 逐字段拷贝，不是 GPU。

### 4.3 950PR 自身的 CPU

纯物理（不渲染）：1/32/64/128/192 进程 = 139 / 4,294 / 7,631 / 11,861 / 12,879 env-step/s，每进程 1.0 核。3.2 节测得每卡吞吐封顶约 69 env-step/s，8 张卡约需 550、整机 16 张约 1,100 env-step/s，CPU 余量 10–20 倍，物理放在本地没有风险。

## 6. ManiSkill 仿真供给

### 6.1 单进程吞吐随 env 数（不含网络，随机动作）

`maniskill_remote_parity.py` 在 GPU 机上直接构造 `pi05_maniskill_1c` 的 env（`PutOnPlateInScene25Main`、640×480 RGB、每个 env-step 100 个 PhysX 子步），每 chunk 5 步，取稳态 chunk 的 env-step/s。

| 卡（主机 vCPU） | 40 env | 80 | 120 | 160 | 上限 |
|---|---:|---:|---:|---:|---|
| RTX 4090 24 GB（180） | 60 | 101 | 147 | 显存不足 | 320 env：GPU 相机组创建失败 |
| RTX 4090 D 24 GB（22） | 58 | 105 | 141 | 显存不足 | — |
| L20 46 GB（30） | 58 | 96 | — | 166 | 320 显存不足；480 相机组创建失败 |
| L4 24 GB（12） | 45 | 80 | 107 | 显存不足 | — |

- **三种卡在同样 env 数下几乎一样快**（差别 ≤5%）。4090 的 FP32 算力是 4090 D 的 1.12 倍、L20 的 1.38 倍，吞吐却不随之变化；`nvidia-smi` 的 SM 占用在 82–97%，说明 GPU 一直有 kernel 在跑，但这个负载是大量小 kernel 的发射与同步主导，不是算力主导。
- **L4 慢约 1/4**：同样 env 数下是其他三种卡的 0.73–0.83 倍。不是功耗墙：满载平均 35 W（上限 72 W），SM 频率一直在 2,040 MHz 的上限。L4 的频率上限比 L20 低 19%（2,040 对 2,520 MHz），显存带宽约为 L20 的 1/3（300 对 864 GB/s），差距应来自这两项，本轮没有再拆分。
- 吞吐随单进程 env 数近线性上涨（40→120 涨 2.4 倍），所以「一张卡能供多少」由单进程能放多少 env 决定，也就是由**显存**决定：24 GB 卡单进程能放 120 个 env、放不下 160 个，L20 放得下 160 个、放不下 320 个。
- 用 π₀.₅ 出的动作时，同样 40 个 env 在服务端约 81–82 env-step/s（第 5 节端到端里每步 3,200 env-step 用 39.0–39.7 s），是随机动作的约 1.35 倍（推测是随机动作造成的接触更多，PhysX 每步迭代更重）。本节的供给数字都是随机动作下的保守值。

### 6.2 多个会话共用一张卡：分时没有收益，MPS 有

一张 GPU 同时服务多张 950PR 时，每张卡的 env 是一个独立会话（独立进程）。P 个进程各 40 个 env 共用一张卡，合计 env-step/s：

| 卡 | 1 进程 | 2 进程 | 3 进程 | 4 进程 | 5 进程 | 2 进程 × 80 env | 3 进程 × 60 env |
|---|---:|---:|---:|---:|---:|---:|---:|
| 4090，不开 MPS | 61 | 61 | 显存不足 | — | — | — | — |
| 4090，开 MPS | 62 | 112 | 显存不足 | — | — | 显存不足（2 × 60 亦然） | — |
| 4090 D，不开 MPS | 58 | 56 | — | — | — | — | — |
| L20，不开 MPS | 58 | 56 | 55 | 56 | — | 94 | — |
| L20，开 MPS | 60 | 102 | 132 | 168 | 190 | 164 | 175 |
| L4，不开 MPS | 45 | 43 | — | — | — | — | — |
| L4，开 MPS | 47 | 78 | — | — | — | — | — |

- **不开 MPS 时，多个会话轮流占用 GPU，合计吞吐等于一个会话**：2 个会话各自只有单独运行时的一半速度。所以不开 MPS 时，一个会话应独占一张卡。
- **开 NVIDIA MPS 后，多个会话的 kernel 并发执行**，合计吞吐接近单进程同等 env 数（L20：2×40 = 102 对 1×80 = 96；2×80 = 164 对 1×160 = 166；4090：2×40 = 112 对 1×80 = 101；L4：2×40 = 78 对 1×80 = 80）。L20 上每个会话的速度随会话数从 60 降到 51、44、42、38 env-step/s（1–5 个会话），合计仍在涨。
- **限制变成显存**：每个 40 env 的 ManiSkill 进程约 7.5–8.6 GB，开不开 MPS 都一样，所以 24 GB 卡最多放 2 个这样的会话（L4 上 2 个会话峰值 17.2 GB，第 3 个放不下，没有再测），46 GB 的 L20 放得下 5 个。
- MPS 的部署细节：控制守护进程放在仿真机容器里（L4 没有容器，放在宿主机上）、用独立的 pipe 目录，只有设置了同一 `CUDA_MPS_PIPE_DIRECTORY` 的进程会接入，不影响同机其他租户；守护进程用 `CUDA_VISIBLE_DEVICES` 限定 GPU 时，客户端看到的设备会**重新编号**为 0、1、…；镜像里 CUDA 13 的 forward-compat `libcuda` 不能用于 GeForce 卡上的 MPS server（4090D 上报 804），需要让守护进程优先加载宿主驱动的 `libcuda`。

### 6.3 4090 D 与 L4 的环境问题

- **4090 D**（驱动 550.90，CUDA 12.4）：镜像里的 torch 是 2.11.0+cu130，消费级卡不支持 CUDA forward compatibility（报错 804），torch 起不来。做法：在容器里另装一份 `torch==2.11.0+cu128`（阿里云 pytorch-wheels 镜像，`pip --target` 叠加到 `PYTHONPATH` 前面，6.6 GB），并让 `LD_LIBRARY_PATH` 先找到宿主驱动的 `libcuda`（否则 ldconfig 先给出镜像里的 compat 版）。cu128 在 550 驱动上靠 CUDA 12.x 的 minor version compatibility 运行，ManiSkill 正常。
- **L4**（驱动 550.144，`.run` 安装，直通）：机器没有镜像，磁盘只剩约 60 GB，拉 33 GB 的镜像过于紧张，所以用 uv 建了只含 torch cu128、ManiSkill 3.0.0b22、SAPIEN 3.0.1 的最小 venv，并从 4090 D 拷了 SAPIEN 首次运行要下载的 PhysX GPU 库（GitHub 不通）。宿主机上 NVIDIA 的 Vulkan ICD（`libGLX_nvidia.so.0`）拿不到 `vkCreateInstance`，SAPIEN 建不了渲染设备。原因是 ICD 初始化时要 `dlopen("libEGL.so.1")`，而宿主机只装了 glvnd 的 `libglvnd0`，没装 `libegl1`（`LD_DEBUG=libs` 能看到这次加载失败）。镜像里有这个包，所以容器里的 ManiSkill 不受影响；L20 宿主机上不进容器也是同样的现象。用 apt 装上 `libegl1` 与 `libvulkan1` 后 Vulkan 正常，驱动本身不用动；apt 连带装了 `libegl-mesa0`、`libgbm1`、两个 Wayland 库，并把已装的三个 Mesa 包从 `23.2.1-1ubuntu3.1~22.04.3` 升到 `~22.04.4`（安全更新）。上一版说「修复需要动驱动安装」是误判。端到端（5.5 节）还要在这个 venv 里跑 env server，它经 `rlinf.scheduler` 引入 ray，所以又补装了 `ray[default]`（2.59.0），torch 保持 cu128 不变。

## 7. 配比与选型

### 7.1 LIBERO：一台 950PR 配一张渲染卡

**需求。** RLinf 的同步 PPO 里，所有卡的 rollout 同步推进，所以按峰值算：每卡约 205 帧/s（每步都渲染），8 卡约 1,640 帧/s，整机 16 卡约 3,300 帧/s；开 `skip_intermediate_renders` 时分别约 330、660 帧/s。

**供给。** 按 4.2 节各卡的饱和点（不含网络），并参考 4.1 节：完整服务每个 worker 满载约 400 帧/s、需要一个核，网络线程另占 CPU。

| 渲染卡 | 价格系数（L20 为 1） | 单卡上限（帧/s） | 可带 950PR 卡数（每步都渲染，峰值） | 可带卡数（skip_intermediate_renders） | 整机 16 张 950PR 的渲染花费 |
|---|---:|---:|---:|---:|---|
| RTX 4090（每卡需 ≥16 核） | 0.756 | 6,690 | 32 | 160 | 0.756 |
| RTX 4090 D（22 vCPU） | 0.756 | 7,090 | 34 | 170 | 0.756 |
| L20（30 vCPU） | 1 | 6,500 | 31 | 155 | 1 |
| L4（12 vCPU，CPU 先满） | 0.474 | 4,320 | 21 | 105 | 开 skip 时 1 张，0.474；每步都渲染建议 2 张，0.948 |

（价格系数是火山引擎的归一系数；4090 即 FF36，4090 D 即 FF36D。）

- **整机 16 张 950PR 配 1 张渲染卡就够**：4090、4090D、L20 都有约 2 倍余量；L4 在每步都渲染时余量较小（4,320 对 3,300，完整服务还要扣掉网络线程的 CPU），建议配合 `skip_intermediate_renders`，或者 8 张 950PR 配 1 张 L4。
- **按价格选**：每步都渲染时，一张 4090 或 4090 D 最省（0.756）：L20 能力相同但贵 1/3，L4 要两张（0.948）。开 `skip_intermediate_renders` 时一张 L4 就够，最省（0.474）。选的实例还要有足够的 vCPU：每步都渲染时 ≥16，开 `skip_intermediate_renders` 时 ≥8。
- **渲染卡在总花费里占比很小**：摊到每张 950PR 只有 0.03–0.06（L20 为 1）。950PR 与 L20 同价时，L4 方案的总花费只比 4090 方案少 1.7%，所以 LIBERO 的渲染卡可以按供货与运维方便来选。
- 两卡端到端（3.3 节）里 16 个 LIBERO 进程共用一张 4090 的 8 个 worker，单卡吞吐保持 99%，与上面按峰值算的余量一致。

### 7.2 ManiSkill：开 MPS 共卡，按 950PR 的单价选 4090 2:1 或 L20 4:1

**需求。** 每张 950PR（每卡 40 env、gbs 640）每步要 3,200 env-step 的仿真。π₀.₅ 出的动作下，一个独占 GPU 的会话约 40 s 做完；整步约 134 s 里，训练与同步的约 80 s 仿真卡完全空闲。同步 PPO 下所有卡的 rollout 同时进行，所以共卡的会话是同时在要算力，第 6.2 节的「多会话共卡」正是这个场景。

**供给。** 一张 GPU 能带几张 950PR，取决于会话怎么共卡：

| 配法 | NPU:GPU | 每步（s） | env 段（s） | 样本/s/卡 | 相对独占 |
|---|---:|---:|---:|---:|---:|
| 每会话独占一张 4090（2 卡实测） | 1:1 | 133.95 | 41.03 | 4.78 | 100% |
| 每会话独占一张 L4（1 卡实测） | 1:1 | 143.36 | 53.40 | 4.46 | 91%（对 1 卡 4090 的 130.70 s） |
| 2 会话共一张 4090，不开 MPS（实测） | 2:1 | 172.56 | 80.27 | 3.71 | 78% |
| 2 会话共一张 4090 + MPS（实测） | 2:1 | 137.22 | 44.22 | 4.66 | 97% |
| 2 会话共一张 L4 + MPS（2 卡实测） | 2:1 | 154.83 | 61.95 | 4.13 | 87% |
| 3 会话共一张 L20 + MPS（3 卡实测） | 3:1 | 148.38 | 54.96 | 4.31 | 90% |
| 4 会话共一张 L20 + MPS（外推） | 4:1 | 151.4 | 58.1 | 4.23 | 88% |
| 5 会话共一张 L20 + MPS（外推） | 5:1 | 157.5 | 64.2 | 4.06 | 85% |

外推方法：env 段 = 独占时的服务端时间 40.66 s × 单会话独占速度 ÷ k 个会话时每个会话的速度（6.2 节 L20 开 MPS 的供给：60 对 51、44、42、38 env-step/s），其余各段取 2 卡实测值。同一方法对「2 会话共一张 4090 + MPS」预测 138.3 s/步（实测 137.2），对「3 会话共一张 L20」预测 148.7 s/步（实测 148.4）；换到更慢的卡也成立：按 L4 的单会话供给 45 env-step/s，预测独占一张 L4 时服务端每步 39.66 × 60 ÷ 45 = 52.9 s（以 1 卡 4090 的 39.66 s 为基准），实测 52.4 s；按开 MPS 时每会话 39 env-step/s，预测「2 会话共一张 L4 + MPS」155.5 s/步，实测 154.8。4、5 会话需要 4、5 张 950PR，本轮可用的空闲卡只有 13–15 号，没有实测。

**价格。** 仿真卡用火山引擎的归一价格系数（L20 为 1）：4090（FF36）与 4090 D（FF36D）0.7561，L4 0.4739。4090 D 与 4090 同价，显存与单会话速度也相同（6.1 节），下面按 4090 计；4090 D 上开 MPS 共卡没有实测。950PR 的价格没有给，记一张 950PR 的单价是 L20 的 x 倍。

**只看仿真卡。** 按 6.2 节的供给（随机动作，每个会话 40 env），每单位价格的 env-step/s：开 MPS 并放满显存时，L20 放 5 个会话为 190，L4 放 2 个为 165，4090 放 2 个为 148；不开 MPS、每卡一个会话时，L4 为 95，4090 为 81，L20 为 58。L20 与 L4 最省，但 L4 的会话慢，L20 一张卡上的会话多，都会拉长 950PR 的每一步。950PR 越贵，拉长的这部分越贵，越该选单会话快、共卡少的配法；950PR 越便宜，仿真卡在总花费里占比越大（4090 2:1 的仿真卡在 x = 1 时占 27%，x = 2 时占 16%），越该选每张 950PR 分摊得少的配法。

**单位成本吞吐。** k 张 950PR 共一张价格系数为 c 的仿真卡时，每张 950PR 承担的花费是 x + c/k（自己的单价，加上分摊的仿真卡），每单位价格的样本/s = T_k ÷ (x + c/k)，T_k 是上表的「样本/s/卡」。下表以一张 L20 的价格为单位：

| 配置 | k（NPU/GPU） | 样本/s/卡 | 每张 950PR 分摊的仿真卡 | x=0.5 | x=1 | x=2 | x=4 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 每会话独占一张 4090（实测，2 卡） | 1 | 4.78 | 0.756 | 3.80 | 2.72 | 1.73 | 1.00 |
| 每会话独占一张 L4（实测，1 卡） | 1 | 4.46 | 0.474 | 4.58 | 3.03 | 1.80 | 1.00 |
| 每卡 80 env，独占一张 4090（实测，1 卡；每次更新的样本量加倍） | 1 | 5.62 | 0.756 | 4.48 | 3.20 | 2.04 | 1.18 |
| 2 会话共一张 4090，不开 MPS（实测） | 2 | 3.71 | 0.378 | 4.22 | 2.69 | 1.56 | 0.85 |
| 2 会话共一张 4090 + MPS（实测） | 2 | 4.66 | 0.378 | 5.31 | **3.38** | **1.96** | **1.07** |
| 2 会话共一张 L4 + MPS（实测） | 2 | 4.13 | 0.237 | 5.61 | 3.34 | 1.85 | 0.98 |
| 3 会话共一张 L20 + MPS（实测） | 3 | 4.31 | 0.333 | 5.18 | 3.23 | 1.85 | 1.00 |
| 4 会话共一张 L20 + MPS（外推） | 4 | 4.23 | 0.250 | 5.64 | **3.38** | 1.88 | 0.99 |
| 5 会话共一张 L20 + MPS（外推） | 5 | 4.06 | 0.200 | **5.80** | **3.39** | 1.85 | 0.97 |

（每格是每单位价格的样本/s，单位价格为一张 L20。加粗为每卡 40 env 的配法里该列最高的，x = 1 时加粗的三格相差约 0.1%；每卡 80 env 那一行改变了训练设置，另计。）

- **950PR 不比 L20 便宜（x ≥ 1）时，选 4090 或 4090 D + MPS 的 2:1。** 它是实测的配法；x = 2 时比 L20 4:1 高 4%、比 L4 2:1 高 6%，x = 4 时分别高 7%、9%。整机 16 张 950PR 配 8 张。
- **950PR 比 L20 便宜（x < 1）时，选 L20 + MPS 的 4:1。** 5:1 还要高约 3%（x = 0.5 时，4:1、5:1 比 4090 2:1 分别高 6%、9%），但整机 16 张 950PR 用 5:1 也要 4 张 L20，和 4:1 一样；二者都是外推值。4090 2:1 与 L20 4:1、5:1 的分界都在 x ≈ 1.0。
- **x 在 1 附近时，这三种配法打平**：x = 1 时相差约 0.1%，x 在 0.9–1.1 之间最多差 1.3%，都小于两次重复之间的差别（5.1 节 1 卡两次相差 1.7%）。这时可以按别的因素选：4090 2:1 是实测，L20 4:1 是外推；MPS 下同一张卡上的会话共用一个 MPS server，一个会话出 GPU 致命错误时可能连带其他会话，一张卡上的会话越多，影响面越大；整机要管理的仿真实例，4090 是 8 个，L20 是 4 个。
- **L4 在任何 x 下都不是最好的**：它比 4090 便宜 37%，但单会话慢约 1/4，2:1 时每张 950PR 的吞吐低 11%（4.13 对 4.66，5.5 节）。x > 0.34 时不如 L20 4:1，x < 1.94 时不如 L20 5:1；只和实测的配法比，x < 0.86 时它才比 4090 2:1 划算。差距不大：x = 1 时比最好的低 1.3%，x = 2 时低 6%。
- **不能开 MPS 时只能 1:1，950PR 越便宜越该选 L4**：同为 1 卡实测（L4 4.46，4090 4.90 样本/s/卡），x < 2.4 时 L4 划算，x 更大时 4090 / 4090 D 划算。两个会话不开 MPS 共一张卡，只在 x < 0.2 时比 L4 独占划算。
- **每卡 80 env、独占一张 4090**：x > 1.5 时它高于所有每卡 40 env 的配法（x = 2 时 2.04 对 1.96；按 2 卡口径扣掉同步开销，分界约在 1.6）。它把每次更新的样本量加倍，与其余各行不是同一个训练设置，学习行为没有验证。
- **与 H20 单卡比**：H20 单卡（同卡跑仿真与训推）是 2.05 样本/s（5.1 节）。若 H20 的单价是 L20 的 h 倍，950PR + 4090 / 4090 D 2:1 更划算的条件是 h > 0.44 (x + 0.38)，例如 x = 1 时 h > 0.61，x = 2 时 h > 1.05。
- **两个仍可挖的余量**：同步 PPO 下仿真卡每步有约 70% 的时间空闲；改用异步 PPO（`train_async.py`）让 rollout 与训练重叠，或让一台仿真机服务多个独立的训练任务，都能把这部分用上，本轮没有测。另外，把每张 950PR 的 env 加到 80 个可以摊薄 env 段（5.4 节）。

## 8. 网络

**容量**（Python 多流探针，GPU 机 → 950PR 方向，Gbit/s；探针在回环上能跑 129 Gbit/s，排除了探针自身的限制）：

| 机器 | 1 流 | 16 流 | 64 流 |
|---|---:|---:|---:|
| 4090 D | 0.44 | 7.06 | 15.8 |
| L20 | 0.34 | 5.16 | 20.1 |
| L4 | 0.31 | 5.22 | — |
| 4090×8 | 0.32 | 5.07 | 19.9 |

单条 TCP 流被限在 0.3–0.44 Gbit/s，总带宽随流数线性上涨，是典型的逐流限速；950PR → GPU 方向没有这个限制（上传 268.6 MB 的 LIBERO 模型连同签名计算只用了 2.3 s）。两种模式都按这个特点设计：渲染远程每个 env 子进程一条连接，整 env 远程每个会话 16 条数据连接并行。

**LIBERO 渲染远程**：

| 项 | 值 |
|---|---|
| 每帧上行 | 约 21 KB（scene 20.5 KiB + 帧头） |
| 每帧下行 | 196,608 B（256×256 RGB） |
| 模型上传 | 每服务每签名一次，268.6 MB |
| 每帧往返（轻载） | 约 5 ms，其中服务端 1.3 ms；约 3.7 ms 是 196 KB 在一条限速流上的传输时间 |
| 8 卡峰值合计 | 约 1,640 帧/s × 217 KB ≈ 2.8 Gbit/s，分散在每个 env 子进程各自的连接上（每条 10–35 Mbit/s） |

**ManiSkill 整 env 远程**（每卡 40 env）：

| 项 | 值 |
|---|---|
| 每 chunk 上行 | 动作 40 × 5 × 7 个 float32，约 5.6 KB |
| 每 chunk 下行 | 35.2 MiB：40 张 480×640 RGB 图像；状态、奖励、info 合计不到 10 KB |
| 每步下行 | 16 个 chunk，约 563 MiB |
| 实测传输 | 每步 0.35–0.39 s（第 5 节 6 次运行），即每 chunk 约 22–24 ms，含两端编解码；约占 step 的 0.3% |
| 等效吞吐 | 约 13 Gbit/s，高于探针测得的 16 流持续 5.1 Gbit/s。每条连接每次只发约 2.2 MiB，推断这种逐流限速允许短突发（令牌桶式） |
| 8 卡合计 | rollout 期间平均每卡约 0.09 Gbit/s；同步 PPO 下各卡在 chunk 边界上几乎同时回包，合计约 280 MiB 的突发 |

两种模式下网络都不是瓶颈：LIBERO 的单流限速只体现为每帧几毫秒的延迟，ManiSkill 的传输时间不到仿真时间的 1%。若能解除逐流限速，LIBERO 每帧往返可降到 1–2 ms，ManiSkill 的数据连接数可以减少。

## 10. 测量口径、更正与未完成

### 10.1 更正：本轮之前的 950PR 运行实际在物理卡 8 上

上一版报告写的「物理卡 15」不对。harness 在启动前设了 `ASCEND_RT_VISIBLE_DEVICES=7`（容器内 7 号即物理卡 15），但 RLinf 的 placement 把索引映射到容器暴露的全部 NPU、并用 `ASCEND_RT_VISIBLE_DEVICES=0` 启动 worker，于是第 3 节 LIBERO 的 POC 与 env 扩展、第 5 节 ManiSkill 第一轮（`ms_remote_1c_r1`）都跑在容器内 0 号、即物理卡 8 上。证据：ManiSkill 第一轮运行中，`npu-smi` 显示它的进程在物理卡 8 上，worker 进程的环境变量是 `ASCEND_RT_VISIBLE_DEVICES=0`；LIBERO 那几轮用的是同一个 harness 和同样的设置，采样器按 7 号卡采到的功耗在整个运行期间都是约 207 W 的空闲值，说明它们也不在 15 号卡上。

影响：这些运行的时间数据有效（窗口内 step_cv < 1%，没有被抢占的迹象；ManiSkill 第一轮运行时物理卡 8 上只有我们的进程），但它们记录的 NPU 功耗与占用是空闲卡的，不能用。之后的运行改为在 placement 里直接写卡号（容器内 5–7 号，即物理卡 13–15），并已用 `npu-smi` 与采样数据核实。根因的修复已在本地分支 `fix/scheduler-visible-device-remap`（`1be8a8fc`：按节点自身的可见设备映射 worker 的设备号），尚未合入 `dev` 和上游。

### 10.2 口径

- **端到端**：用 TC1 的 harness（`run_arm.sh`）与梯级配置，开 TC1 armB 的模型开关（`npu_fused_attention`、`npu_fused_rms_norm`、`npu_fused_rope`、`skip_masked_images`），LIBERO 另开 `skip_reset_renders`。LIBERO 跑 12 步取后 8 步，ManiSkill 跑 10 步取后 6 步（每卡 80 env 那次 8 步取后 5 步），评测跑 1 遍 500 局；`aggregate.py` 从 TensorBoard 事件读数，窗口内 step_cv 超过 10% 的运行拒收（本轮最高 2.0%，LIBERO 整 env 远程那一次）。
- **重复次数**：ManiSkill 1 卡 2 次，其余每格 1 次，没有做 TC1 那样的 3 次重复；表里的「±」只在 n ≥ 2 时给出。
- **仿真供给**：第 4、6 节的供给曲线不含 NPU，在 GPU 机上直接驱动 env；ManiSkill 用随机动作，比 π₀.₅ 出的动作慢约 1.35 倍（6.1 节），所以是保守值。
- **价格**：仿真卡用火山引擎的归一价格系数（L20 为 1；4090、4090 D 0.7561，L4 0.4739），11-02 由需求方提供；950PR 的价格未给，第 7 节以它相对 L20 的倍数 x 为参数出表。

### 10.3 ManiSkill 的 success_once 与 H20 的对照

| 运行 | 卡 | success_once（窗口均值） | 每卡轨迹数 |
|---|---|---:|---:|
| H20 1 卡 × 3（TC1） | 同卡仿真 | 0.399 ± 0.037 | 52.2 |
| 950PR 1 卡 r1 / r2 | 4090 独占 | 0.293 / 0.325 | 47.7 / 50.2 |
| 950PR 2 卡 | 4090 各占一张 | 0.429 | 52.9 |
| 950PR 2 卡 | 共用一张 4090 | 0.472 | 55.7 |
| 950PR 2 卡 | 共用一张 4090 + MPS | 0.422 | 53.3 |
| 950PR 3 卡 | 共用一张 L20 + MPS | 0.474 | 55.3 |

单卡两次偏低，两卡、三卡都在 H20 的范围或之上，没有一致的方向。同一次运行里相邻两步的 success_once 就能差 0.1–0.15（每步只有 40–120 个 env、50–170 条轨迹），10 步、取后 6 步的窗口不足以分辨 0.05 量级的差异。远程 env 与本地逐位一致（2.3 节），所以这些差异来自 NPU 与 GPU 训练的数值差异、PhysX 在不同 GPU 上的浮点差异与抽样噪声，与远程层无关；要比较学习行为，应按 TC1 的口径用固定 checkpoint 做评测，或跑更长的训练。
