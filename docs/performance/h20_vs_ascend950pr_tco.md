# H20 与昇腾 950PR 的性价比对比（π₀.₅ / GR00T N1.7 · LIBERO / ManiSkill）

本报告给出同一套代码、同一组配置在 **NVIDIA H20** 与 **昇腾 950PR** 上的实测吞吐、
MFU 与盈亏平衡成本比。成本模型：H20 单卡成本记 1，950PR 记 H20 的 **x** 倍；
每一级卡数都给出盈亏平衡的 x，换掉系数即可得到结论，不需要重测。x 现在已由双方的
整机月租报价填入（第 7.2 节），950PR 一侧是暂定价，折扣谈定后只改那一个数。

> 本轮覆盖两个模型 × LIBERO-Spatial，外加 π₀.₅ × ManiSkill。**π₀.₅**（第 4–7 节）1/4/8 卡，950PR 每格两个臂、
> H20 的 1、4、8 卡各三个臂；**GR00T N1.7**（第 8 节）
> 两边 1/4/8 卡各两个臂，**三级都已收齐**。每臂 3 次 run，两边全部在代码树 `f5c7f951` 上、工作区干净。
> **8 卡这一级现在有跨平台了。**H20 的容器原先只分到 6 张卡、运行中改不了，
> 已按 8 张卡重建（10 节第 1 条）。口径一（都 OSMesa）x = **1.737**，是 armA 三级里
> 最高的一格，但它有一部分来自宿主 CPU 规模而不是芯片（5.5 节）；
> 口径二（H20 开 EGL）x = **1.056**，和 1 卡的 1.079、4 卡的 1.052 一致 ——
> 这个口径在三级卡数上是平的（5.6 节）；口径三（开关都开、都 OSMesa）x = **1.827**，
> 是全部九格里最高的（5.7 节）。
> **GR00T 的 8 卡也收齐了**（两条臂各 3 个 run）：口径一 x = **1.421**、口径二 x = **0.683**，
> 方向和 1、4 卡一致，8.6 节那条行为分叉在 8 卡上原样复现 —— 而且 8 卡的 EGL 臂
> 把"H20 侧渲染不对"这个候选排除了（第 8 节）。
> **ManiSkill 两个口径的 1 卡与 4 卡都收齐了，而它们给出相反的结论**（第 9 节）：
> 两边跑同一份活时 x = **2.141 / 1.963**（口径一，全报告最高的两个 x，9.6 节），
> 各平台用自己最优的方式跑时 x = **0.798 / 0.711**（口径二，9.4 与 9.5 节）——
> **同一对硬件、同一个模型、同一个仿真器，两个口径差 2.7 倍**，
> 因为 H20 能把每卡的环境数从 1 个开到 40 个而 950PR 开不了（9.1 节）。
> 两个口径的 x 都随卡数跌（和 LIBERO 相反），8 卡两边都没有。
> **一条新发现的口径缺陷，三级卡数都已补测：**`skip_reset_renders` 只开在 950PR 的 armB 上，
> H20 的 π₀.₅ 臂漏了。补测把六个格子全部从外推换成实测：**口径三
> 1.731 / 1.766 / 1.866 → 1.707 / 1.725 / 1.827，口径二 1.083 / 1.051 / 1.066 →
> 1.079 / 1.052 / 1.056**（1 / 4 / 8 卡）—— 那个开关在 OSMesa 下砍掉 13%–17% 的
> `bootstrap_step`、在 EGL 下只有 1%–4%（5.7 节）。
> 8 卡那一格的两个 run 被邻居的 70 GiB 作业打断过（一个 OOM、一个窗口被占），
> 重跑后 x 从 1.837 落到 1.827，判废是对的（5.7 节末）。
> **功耗也补上了：八格里 950PR 全部更费电（多 15%–175%），但那只值 1.3–2.7 个百分点**（6.5 节）。
> 缺口在第 10 节逐条列出；这一轮排过哪些队列、什么还没做，在第 12 节 ——
> 交付时两台机器上都没有队列在跑。

## 1. 结论

**一句话：结论取决于模型，也取决于仿真器。π₀.₅ × LIBERO 上 950PR 在所有已测口径下
都更便宜，吞吐也不落后；GR00T N1.7 上，H20 一旦开 GPU 渲染就反超，按现在的报价两边
大致打平；同一个 π₀.₅ 换到 ManiSkill，连"哪个口径"都能把结论翻过来 ——
两边跑同一份活时 950PR 快一倍多（x = 2.141 / 1.963），各平台用自己最优的方式跑时
H20 反超（x = 0.798 / 0.711），两个口径差 2.7 倍。
分界线不是芯片，是仿真占 step 的比例，以及那一段能不能搬到 GPU 上。**

> GR00T 那一格带一条保留：同样的权重与配置下，两边的任务成功率差 2.3–2.7 倍，
> 每步做的 reset 次数也随之不同（8.6 节）。方向上的反转大概率成立，
> 但幅度要等这件事定位之后才能定。π₀.₅ 没有这个问题 ——
> 那边每步的 trajectory 数被配置固定，两边完全一致。

π₀.₅ × LIBERO（本报告第 4–7 节的主体）：

| 部署形态 | 1 卡 | 4 卡 | 8 卡 |
|---|---:|---:|---:|
| 渲染在 CPU 上，开关全关（两边都 OSMesa） | 省 **57%** | 省 **58%** | 省 **60%** |
| 渲染在 CPU 上，开关都开（两边都 OSMesa） | 省 **59%** | 省 **59%** | 省 **62%** |
| H20 用 GPU 渲染（EGL） | 省 **35%** | 省 **33%** | 省 **34%** |

后两行六格现在全部是对称口径的实测值（5.7 节），`skip_reset_renders` 只开在 950PR
一侧的那个不对称已经消掉。第一行三级本来就不受影响 ——
那个口径两边的 override 列表都是空的。
**这张表只算租金。**加上电费（950PR 每份活多耗 15%–175% 的电）各格再降 1.3–1.7 个百分点，
方向不变（6.5 节）。

GR00T N1.7 × LIBERO（第 8 节，三级都已完整，但要带 8.6 节那条保留）：

| 部署形态 | 1 卡 | 4 卡 | 8 卡 | |
|---|---:|---:|---:|---|
| 渲染在 CPU 上（两边都 OSMesa） | 省 **48%** | 省 **51%** | 省 **51%** | 偏保守 |
| H20 用 GPU 渲染（EGL） | **贵 1%** | **省 2%** | **贵 2%** | 偏向 H20 |

GR00T 的三个 EGL 口径是本轮唯一三格 950PR 在吞吐上落后的（盈亏平衡 x = 0.692 / 0.716 / 0.683，
区间整体 <1），而这三个数落在报价区间 0.625–0.786 的中间，所以成本上两边打平：
中位价上是 省 2% 到 贵 2%，整个价格区间里是 省 13% 到 贵 15%。
最后一列是 8.6 节那条保留的方向：950PR 每步多做约 1.54–1.58 倍的 reset，
所以 OSMesa 那三格的优势被低估、EGL 那三格的劣势被高估。

π₀.₅ × ManiSkill（第 9 节，两个口径的 1 卡与 4 卡都已收齐，8 卡两边都没有）：

| 部署形态 | 1 卡 | 4 卡 | |
|---|---:|---:|---|
| 两边同一份活（都 CPU 物理 + 软件光栅化） | 省 **63%–71%** | 省 **60%–68%** | 全报告最高的两个 x |
| 各平台最优（H20 开 GPU 物理 + EGL） | 省 **1%–22%**，可能贵 **2%** | 省 **12%** 到贵 **11%** | 两边活量差 40 倍 |

**这一格最该带走的不是某一个数，是这两行的距离。**盈亏平衡 x 分别是
**2.141 / 1.963**（口径一）与 **0.798 / 0.711**（口径二）—— 差 2.7 倍，
而两行用的是同一对机器、同一个模型、同一个仿真器、同一批代码。
分开它们的只有一件事：H20 能把每卡的环境数从 1 个开到 40 个，950PR 开不了（9.1 节）。
口径一那两格是本报告最偏算力的读法（加速器占 H20 一步的 61.8%），
所以它给出最高的 x；口径二那两格跨着两种形状的负载，所以比 LIBERO 那六格弱。
两个口径的 x 都随卡数跌（和 LIBERO 相反），因为 950PR 在 ManiSkill 上的扩展
比 H20 差 8–10 个百分点，损失在 actor 的 all-reduce 上（9.3 节）。读法见 9.4 与 9.6。

**为什么同一对硬件会给出两个方向的结论：**加速器上 950PR 在两个模型上都快
（1 卡：π₀.₅ 1.84 倍、GR00T 1.77 倍 —— 但 GR00T 的这一项到 8 卡会掉到 1.32 倍，
因为 950PR 的梯度 all-reduce 比 H20 贵 3.1 倍，8.3 与 8.5 节），
但加速器占 step 的比例差了一倍 ——
在 H20 上，π₀.₅ 的加速器两项占 step 的 49%，GR00T 只占 **17.8%**。
GR00T 剩下的 78% 是 CPU 仿真，而那一段 H20 能用 EGL 搬到 GPU 上（−72%），
950PR 没有图形栈可搬。所以**这个对比的分界线是"仿真占多少"，不是"芯片谁快"** ——
选型时该先量自己工作负载的这个比例，再看芯片。8.3 节把这条拆开算了一遍。

价格用的是整机月租：H20 96G 3.5 万–4.0 万/月/8 卡，950PR 暂定 5.0 万–5.5 万/月/16 卡，
折成单卡成本 **x = 0.625–0.786**（中位价对中位价正好 0.700）。实测吞吐算出的盈亏平衡 x
是 1.629 / 1.658 / **1.737**（1、4、8 卡，开关全关、都 OSMesa）、
**1.707 / 1.725 / 1.827**（1、4、8 卡，开关都开、都 OSMesa）、
**1.079 / 1.052 / 1.056**（1、4、8 卡，H20 开 EGL）—— 真实的 x 在每一格都更低，所以每一格 950PR 都划算，
而且**九格的盈亏平衡 x 都大于 1，意味着 950PR 在吞吐上也更快**。
九格现在全部是对称口径的实测值，没有一格靠外推（5.7 节）。
最大的一格是 8 卡的口径三（1.827，5.7 节），最小的是 4 卡的 EGL（1.052 [1.037, 1.067]）。
剩一条保留：开关全关那一行的 8 卡 x 有一部分来自宿主机 CPU 规模而不是芯片（5.5 节）。
GR00T 的六格是 1.357 / 1.419 / **1.421**（1、4、8 卡，都 OSMesa）与
**0.692 / 0.716 / 0.683**（1、4、8 卡，H20 开 EGL），后三格整体小于 1
（区间 [0.663, 0.723]、[0.695, 0.739] 与 [0.670, 0.695]），详见第 8 节。

H20 的 1 卡与 4 卡都有三条臂，所以两级都能把 H20 的两个杠杆拆开（4.1 与 5.1）：
**开关只值 6.33%（1 卡）/ 5.49%（4 卡），剩下的 37%–40% 全是 GPU 渲染。**
把渲染后端按住、两边都开自己的内核时（口径三），x 是 **1.707 / 1.725 / 1.827**（1/4/8 卡）——
π₀.₅ 九个口径里最大的三格。

最紧的一格是 4 卡 + H20 开 EGL，那里 950PR 还有 1.34 倍余量（最坏价格角落）：它要报到
7.4 万–8.4 万/月/16 卡才会打平。价格表和逐格成本比见第 7 节；盈亏平衡 x 本身不含价格假设，
折扣谈定后换系数即可，不需要重测。

**但这整栏有一个前提：16 卡的机器得填满。** H20 一台 8 卡、950PR 一台 16 卡，
一个 8 卡作业填满一台 H20 却只填半台 950PR，有效单卡成本翻倍、有效 x 变成 1.25–1.57 ——
那一档上 H20 能用 GPU 渲染的话 950PR 反而贵 30%–33%。这是比价格更能决定结论的一个条件，
见 7.4 节。

逐条：

1. **加速器上 950PR 快 1.8–2.2 倍，整机上快 5%–77%。** 加速器阶段 950PR 快
   1.800 倍（armA 4 卡）到 2.196 倍（armB 4 卡），但渲染在 CPU 上时主机侧占了 step 的 59%–69%，
   而 950PR 只能用 CPU 软渲染。
2. **1 卡这一级，H20 开 EGL 后仍然慢 7.9%**（69.988 s 对 64.872 s），4 卡慢 5.2%
   （72.328 s 对 68.757 s）。EGL 让 H20 的主机阶段比 950PR 快 1.65 倍，但补不回加速器上的 2.2 倍。
   **这一条和早先的报告相反** —— 早先那个"H20 开 EGL 后反超 7.8%"的结论用的是争用下的
   950PR 数字，安静窗口把它翻过来了（2.5 节）。
3. **同机 CPU 争用是这份对比最大的单项误差，它已经被量化并消除。** 邻居占 30 个 CPU
   百分点时，950PR 的 step 慢 10%–22%。判别办法和对照见 2.5 节 ——
   最硬的一条是 armA 8 卡那一格的四个安静 run 分属两棵不同的代码树、彼此只差 0.5%。
4. **950PR 的弱扩展：4 卡 95%、8 卡 90%**（每卡工作量不变）。加速器侧与主机侧涨幅相当
   （1→8 卡 +10.4% 与 +11.4%），所以扩展损失没有单一来源。
   早先报的"1→4 卡只涨 1.69%、效率 98.3%"是争用造成的假象（5.4 节）。
5. **950PR 算力富、带宽穷。** 被测卡实测 bf16 GEMM 上限 369.5 TFLOP/s 对 H20 的
   139.8 TFLOP/s（**2.643 倍**），但 HBM 带宽 1347 GiB/s 对 3134 GiB/s（**0.430 倍**）。
   加速器阶段实测只拿到 1.8–2.2 倍而不是 2.64 倍，与这个结构一致。
   跨 UB 岛（物理 8–15）极差只有 0.32%，所以 8 卡的 MFU 分母和 4 卡是同一个。
6. **MFU 把差距的性质说清楚了：950PR 缺的不是算力。** armA 1 卡加速器阶段 MFU 为 H20
   **55.6%** 对 950PR **38.7%** —— 2.64 倍的上限只兑现成 1.84 倍的吞吐，差额去了访存。
   各平台最优口径下是 65.2% 对 51.7%，**950PR 开上自己的内核后已接近 H20 不开优化的
   55.6%**。但按整个 step 算（分母含渲染）是 **46.1% 对 18.4%，差 2.5 倍**：这是"缺图形栈
   的代价"最直接的一个数，也是和成本挂钩的那个。
7. **两边的 armB 都在少算，不只是算得快。** 950PR 的 `skip_masked_images` 砍掉 rollout
   3.14%、actor 4.74% 的 FLOPs；H20 的 `enable_fused_prefix` 砍掉 actor 2.97%。
   每步总算力：H20 armB 比自家 armA 少 1.16%，950PR armB 少 3.79%，950PR armB 比 H20 armB
   少 **2.76%**。所以口径二加速器阶段那 2.155 倍（1 卡），折算成同等算力是 **2.096 倍**。
   armA 对 armA 两边算力只差 0.10%，是真正的同一份活。
8. **开关收益完全不随卡数衰减，而且逐阶段都不衰减。** 950PR armB 对 armA 的 step 收益
   1/4/8 卡是 −11.87% / −11.28% / −11.42%，加速器阶段是 −27.93% / −28.18% / −27.27%，
   三级之差都在 1 个百分点以内。
9. **950PR 每做同样一份活多耗 15%–175% 的电，但那只值 1.3–2.7 个百分点**（6.5 节）。
   八个格子全部是 950PR 更费电，因为它每卡的功耗是 H20 的 1.32–2.03 倍，
   而速度只有 0.69–1.66 倍；空闲底噪也差 2.74 倍（203 W 对 74 W）。
   按中位租金加 0.7 元/kWh 折算，电费让各格的成本比上浮 1.3–2.7 个百分点，
   **只有 GR00T 4 卡口径二被推过了分界线（省 2% → 打平）**，其余方向不变。
   要抹平 π₀.₅ 4 卡口径一的租金差，电价得到 86.8 元/kWh。
   H20 自己的两个杠杆在能耗上的账也相反：开关买时间不买电（每步能耗 +4%），
   EGL 两头都赚（−27%，GR00T −50%）。

## 2. 方法

### 2.1 两个臂

每一级卡数跑两个臂，各重复 3 次：

| 臂 | 含义 | H20 | 950PR |
|---|---|---|---|
| **armA** | 平台开关全关，渲染都用 OSMesa | 无 override | 无 override |
| **armB** | 各平台自己的最优开关 | fused prefix（actor）+ rollout 图编译 | 融合 attention / RMSNorm / RoPE + `skip_masked_images` + `skip_reset_renders` |

armA 是控制臂：两边的 override 列表都是空的，所以它是"同一套代码、同一组配置"这条要求
唯一能严格成立的口径。armB 是各平台最优口径，按需求方确认的"各平台最优当主口径"。

**这张表里有一处不对称要先说清楚：`skip_reset_renders` 只在 950PR 的 armB 里。**
它是 LIBERO env 的开关、两个平台都有（GR00T 那一节的 armB 两边都开着它，8.1 节），
所以 π₀.₅ 的 H20 臂里没有它是臂定义时漏的。
受影响的是用到 armB 的两个口径（口径二与口径三）。
**三级卡数都已补测**：口径三的 x 从 1.731 / 1.766 / 1.866 落到 1.707 / 1.725 / 1.827，
口径二从 1.083 / 1.051 / 1.066 落到 1.079 / 1.052 / 1.056（1 / 4 / 8 卡）。
细节在 5.7 节。口径一三级都不受影响。

渲染后端是 armB 在两边不对等的地方。**950PR 完全没有图形栈**，OSMesa（CPU 软渲染）
是它唯一能跑的后端；H20 可以用 EGL 走 GPU 渲染。所以 H20 侧跑三条臂而不是两条：

| H20 的臂 | 开关 | 渲染 | 用来回答 |
|---|---|---|---|
| `armA_sw_off` | 无 | OSMesa | 口径一，与 950PR armA 严格同配置 |
| `armB_h20_sw` | 有 | OSMesa | 把开关的效果和 EGL 的效果分开 |
| `armB_split` | 有 | EGL | 口径二，H20 的真实最优 |
| `armB_h20_sw_srr` / `armB_split_srr` | 有，再加 `skip_reset_renders` | OSMesa / EGL | 补上这张表上面说的那处不对称（5.7 节） |
| `armB_h20_sw_nocmp` / `armB_split_nocmp` | 有，但关掉图编译 | OSMesa / EGL | 把 EGL 对加速器的代价和图编译自己的效果分开（4.1 节末） |

`armB_h20_sw` 这一条不是为了对比而加的，是为了**归因**：没有它，H20 armB 对 armA 那
41% 的收益分不清有多少来自开关、有多少来自 EGL。

H20 的 EGL 曾在本机 >2 卡确定性崩溃，重启后恢复（10 节第 5 条），所以 4 卡这一级
现在有实测的 EGL 臂；早先版本里 4 卡口径二改用 OSMesa 对 OSMesa，那个退让已经不需要了。

### 2.2 弱扩展梯级

`toolkits/perf_compare/make_rung_configs.py` 从 `libero_spatial_ppo_openpi_pi05.yaml`
生成 1/4/8 卡的梯级配置，**每卡工作量不变**：每卡 8 个 env、global batch 64、
micro batch 16、horizon 240。卡数写进配置文件而不是命令行 —— 它来自 Ray 的加速器探测，
`CUDA_VISIBLE_DEVICES` / `ASCEND_RT_VISIBLE_DEVICES` 都改不动它。

两台机器上的梯级配置逐字节相同。

### 2.3 每个 run 记什么

`run_arm.sh` 把这些落在结果旁边：开关集、渲染后端、步数、模型路径、venv、
**代码树哈希**、工作区脏文件数、设备节点列表、栈版本（torch / torch-npu / ray /
transformers / mujoco / robosuite）。

**代码身份用树哈希而不是 commit 哈希**：两台机器打同一串 patch 会得到不同的 commit
哈希、相同的树，而对比要求的是树相同。**本报告引用的全部测量 run 都在树 `f5c7f951`
上、工作区零脏文件**，两台机器逐字节同一棵树 —— "同一套代码"这条要求是直接成立的，
不需要任何论证。

早期有一批 run 在树 `bd6b37ea` 上（H20 最早的 armA 基线更早，在 `d33e9358` 上且工作区
有脏文件）。那批数据不进本报告的任何一张表。两棵树的差异逐行核对后全部落在
`if counting:` 与 `if configured:` 里，是 FLOPs 计数的日志行。
**但代码树只被审读排除，没有被测量排除。** 盘过磁盘上的全部 run 之后：
`bd6b37ea` 那 15 个 run 全是 1 卡与 4 卡，而且**全部是争用下测的**
（邻居 CPU 23.7–39.1），没有一个落在 8 卡；所以没有任何一格同时有两棵树的安静 run，
拿不出跨树的对照。早先这里写过一个"≤0.5% 的测量上界"，那是把 8 卡 armA
四个安静 run 当成分属两棵树了 —— 它们实测都在 `f5c7f951` 上，
那 0.5% 量的是五小时内的时间漂移，不是代码树（2.5 节）。

每个 run 跑 12 步，取**后 8 步**作为稳态窗口；表中 `±` 是 **run 间**标准差。

**run 内也要稳。** run 间标准差看不见一种失效：一个 run 在大部分步上和同格邻居分毫不差、
在少数步上停顿，它的均值就落在它自己任何一步都没有到过的地方。所以每个 run 还报窗口内的
相对标准差 `step_cv`，超过 10% 的 run 被拒绝而不是平均进去（`aggregate.py`）。
这条线是事后补的，所以本轮全部 run 都回查过一遍，两台机器各查一次：

| 窗口内 `step_cv` | 950PR | H20 |
|---|---|---|
| π₀.₅ × LIBERO | 0.2%–2.4% | 0.3%–1.3% |
| π₀.₅ × ManiSkill | 0.8%–2.9% | 0.7%–0.8% |
| GR00T N1.7 × LIBERO | 1.2%–6.2% | 1.5%–8.0% |

已发表的格子里没有一个 run 越线，最高的是 H20 的 GR00T armA 1 卡 r2（8.0%）；
唯一越线的是 950PR 8 卡 armA 的第三次重跑（19.4%，见 10 节第 7 条）。
**GR00T 整体高出一档在两台机器上各自独立成立**，所以那不是某一边的怪象，
是这个负载本身的性质，见 8.6。

### 2.4 开关指纹

一个静默失效的开关会给出看起来合理的数字、挂在错误的臂名下。两道门：

- `run_arm.sh` 的 `EXPECT` / `REJECT`：每个开关各一条必须出现（或必须不出现）的日志行。
  950PR 的融合算子引擎时不打日志、只在平台不对时打回退警告，所以那边用 `REJECT`。
- `switch_probe.py`：用 `TorchDispatchMode` 驱动真实的 `gemma.Attention` 与
  `gemma.RMSNorm`，断言 `npu_fusion_attention` / `npu_rms_norm` / `npu_rotary_mul`
  确实进了 dispatcher。开关打开而算子没出现就退出 1。

**已知缺口**：rollout 图编译没有日志行，`EXPECT` 覆盖不到它。

### 2.5 同机争用是一个一阶误差项，不是噪声

两台机器都是共享的。**950PR 这一侧，同机其他租户的 CPU 占用能把 step 时间推高 22%**
—— 比本报告里任何一个开关的效果都大，所以它必须被当成一个被测量的量，而不是被当成
run 间离散度吸收掉。

armA 的渲染全在 CPU 上，所以邻居的 CPU 爆发直接落在被测路径上。
度量办法：采样器记整机 CPU 百分比（`power.csv` 的 `host_cpu_pct`），
自己那一份由安静窗口定出来 —— **1 卡 ≈ 3.1%、4 卡 ≈ 13.0%、8 卡 ≈ 25.3%，逐卡线性**，
减掉之后剩下的就是邻居。

把每一格里的 run 按邻居 CPU 排序（单位是整机 CPU 百分点，950PR 宿主 256 线程，
所以 30 点约等于 77 个线程被别人占着）—— **"邻居 ≈0"与"邻居 >10"两组之间每一格都干净分开，
中间没有重叠**；组内部的次序只是大致单调，因为 `host_cpu_pct` 是整个 run 的均值，
而邻居的爆发在 run 内部不均匀：

| 格子 | 按邻居 CPU 排序的 run：邻居 CPU → `time/step` |
|---|---|
| armA 8 卡 | 0 → 81.334　0 → 81.445　0 → 81.527　0 → 81.705　**31 → 99.309** |
| armA 1 卡 | 0 → 73.531　0 → 73.268　0 → 74.030　**32 → 85.348　34 → 85.508　35 → 86.113** |
| armA 4 卡 | 0 → 77.143　1 → 77.513　1 → 77.838　**13 → 86.925　20 → 86.387　26 → 88.000** |
| armB 4 卡 | 0 → 68.465　0 → 68.716　1 → 69.092　**11 → 72.659　22 → 76.931　23 → 76.728** |
| armB 8 卡 | 1 → 71.961　1 → 72.145　1 → 72.158　2 → 72.207　2 → 72.339　2 → 72.589 |

这套模型后来被一次事前验证撞上了：补 8 卡 armA 第三个 run 时（10 节第 7 条），
其中一次的邻居 CPU 约 6 个百分点，step 87.333，比同格两个安静 run 慢 **7.0%**。
模型是回头排序得出的，这一条是先有模型、再在新窗口里撞上的 —— 方向和量级都对得上。

两行是对照，它们把"这是争用"从相关性变成了判别：

- **armA 8 卡那一行有四个安静 run，跨五小时（05:31–10:43）彼此只差 0.46%**，
  唯一的离群 run 邻居 CPU 31。所以不是时间漂移，也不是卡的状态漂移。
  四个 run 都在代码树 `f5c7f951` 上，所以这一行**不能**用来给代码树的影响定上界 ——
  磁盘上 `bd6b37ea` 的 run 全在 1/4 卡且全部争用，没有可比的安静对照（2.3 节）。
- **armB 8 卡六个 run 全部安静，全部落在 71.96–72.59**。这一格重测前后不动 ——
  那不是反例，那正是机制该有的样子：没有邻居，就没有可修的东西。

还排除了两条：物理卡（4 卡那个安静的确认 run 用的是同一组卡 8–11）与采样器
（两批 run 的采样器是同一份）。

两台机器的争用情况不对称，而且这个不对称是运维事实而不是硬件事实：

| | 950PR 宿主 | H20 宿主 |
|---|---|---|
| 1 分钟负载 p50 / p90 / 峰值 | 35.0 / 75.9 / 103.5 | **0.67 / 4.73 / 18.98** |
| 占 CPU 的邻居 | 其他租户的 vLLM、python3、cc1plus（4–5 个容器） | 只有 `containerd` 与 `cloud-monitor`（各 ~7.8%） |
| 测量期间自己以外的 CPU | 要等窗口 | 默认就是干净的 |
| 共享的加速器 | 卡 12–15 和另一租户的 vLLM 重叠 | **八张卡全部和 `NVIDIA_VISIBLE_DEVICES=all` 的 pod 重叠** |

（950PR 的负载数里含自己那一份；邻居的判定用 `host_cpu_pct` 减掉自己那份，见上。）

**但"干净"只对 CPU 成立 —— H20 的 GPU 是共享的，而且已经吃掉了一个 run。**
ManiSkill 口径二 4 卡的第一个 run（`msh20_armB_4c_r1`）死在 CUDA OOM：
报错时卡 0 的 95.33 GiB 只剩 230 MiB，我们自己的三个进程占 45.1 GiB
（22.78 + 13.67 + 8.65），而**另有一个不在我们容器 pid 命名空间里的进程占着 49.97 GiB**。
这台机器上有多个 k8s pod 以 `NVIDIA_VISIBLE_DEVICES=all` 跑着
（`dongmao-pi05-bench`、`rlinf-0`、`gpu-viewer`），所以八张卡没有一张是独占的。
（这个 run 后来在安静窗口里重跑成功，那一格现在是 n=3，9.5 节。）

这和 950PR 那边 8 卡停顿是同一类机制、不同症状：那边是另一个租户的 vLLM 占着
卡 12–15（10 节第 7 条），表现为 run 内停顿；这边是一次抢走 50 GiB，表现为 OOM 直接失败。
**失败比停顿好** —— 失败留痕迹，停顿不留。

对此加了两层，两边通用：

- 每个 run 起跑前等整机的卡都空（`ms_common.sh` 的 `wait_gpus_quiet`，
  `GPU_GATE_MIN` 分钟后仍不空就照跑并在日志里写明，不静默等待）。
  它只看起跑前的状态，防不住跑到一半进来的邻居。
- 宿主侧的 `gpu_neighbour_watch.sh` 每 30 秒记一次逐卡显存，外加**所有不属于我们
  pid 命名空间的占卡进程**（pid 与占用量）。这是为了事后把一次停顿或 OOM 归到具体的
  外来进程上 —— 正是 950PR 那次停顿缺的那条通道。

**所以本报告的 950PR 数字全部取自一个安静窗口**，每一格都报它的实测 `host_cpu_pct`。
早期那批在争用下测的数字偏慢 7%–16%，不进任何一张表 —— 它们只会让盈亏平衡 x
偏保守，但"偏保守"不是精度。

## 3. 硬件与环境

### 3.1 两台宿主机的 CPU 不对称

| | 950PR 宿主 | H20 宿主 |
|---|---|---|
| CPU | 2× AMD EPYC 9A75（64 核） | 2× Intel Xeon Platinum 8457C（45 核） |
| 线程 | **256** | **180** |
| 内存 | 1511 GiB | 1929 GiB |
| 测量窗口内自己以外的 CPU | 已等到 ≈0（见 2.5） | ≈0（该机常态） |
| 容器运行时 | docker | nerdctl（无 docker） |

armA 两边都用 OSMesa，主机阶段（`env_interact_step` + `bootstrap_step`）占 step 的
**59.2%（H20）与 63.4%（950PR）**，渲染全在 CPU 上，所以 armA 实际是**整机对比**，
不是隔离加速器的对比。950PR 多 42% 的线程是它真实的优势，而且这一轮它能用上 ——
早先那批数字里这个优势被邻居吃掉了（2.5 节）。

**两边都不设 CPU 亲和**（单边设就是不对称），改为把争用当成被测量的量：
等到两台机器各自的邻居 CPU 都降到 0 再测，并逐 run 记录。
宿主 CPU 规格的差异不从结论里剥出来 —— 买的是整机，付的是整机价（7.2 节）。

### 3.2 逐卡健康与 MFU 分母

被测卡是 950PR 的物理 8–15（UB 岛 C 与 D）与 H20 的容器设备 0–3。
`hw_ceiling.py` 在被测卡、被测 venv 下实测：

| | 卡数 | bf16 GEMM 峰值均值 | 极差 | 取得峰值的形状 | HBM 拷贝均值 |
|---|---:|---:|---:|---|---:|
| 昇腾 950PR（物理 8–15） | 8 | **369.5** | 0.32% | 8192³ | 1347 GiB/s |
| NVIDIA H20（容器 0–3） | 4 | **139.8** | 1.04% | 16384³ | 3134 GiB/s |

单位 TFLOP/s。两边都没有一张卡在拖低结果，**跨 UB 岛也没有**：岛 C 与岛 D 的八张卡
极差 0.32%，所以 8 卡这一级的 MFU 分母和 4 卡是同一个。
MFU 分母按每一级实际用到的那组卡取。

950PR 在 16384³ 反而掉到 332–343 TFLOP/s，H20 则在 16384³ 才到峰值；两者峰值出现在不同
形状，所以 MFU 分母取各自在实测形状上的峰值，并注明形状 —— 把分母固定到同一个形状
会让某一方为它并不擅长的形状付账。

**GEMM 上限 2.643 倍、HBM 带宽 0.430 倍**，这个结构是本报告大部分现象的来源。

### 3.3 Ascend 容器的设备模型

必须显式 `--device /dev/davinciN`，不能用 `--privileged`：Ray 数的是容器能看到的加速器，
RLinf 的卡数来自 Ray，而 `ASCEND_RT_VISIBLE_DEVICES` 覆盖不了它 —— privileged 容器会报
全部 16 张卡。列出设备同时也避开别人占着的卡，而 Ascend 设备节点一次只容一个容器，
抢占会让对方的任务收到 `Resource_Busy(EL0005)`。

**编号要分清**：设备节点在容器里保留宿主名字（`/dev/davinci8` 还叫 davinci8），
但 torch_npu、Ray 和**容器里的 npu-smi** 都从 0 开始给暴露出来的那一组编号 ——
容器里 `npu-smi -i 8` 会答 "Invalid card id"。所以 run 同时记设备节点列表和
`RLINF_PERF_HOST_CARDS`。

### 5.4 弱扩展：950PR 8 卡 90.3%，H20 84.7%

每卡工作量不变，所以 step 时间的涨幅就是扩展损失：

| | 1 卡 | 4 卡 | 8 卡 | 1→4 加速比 / 效率 | 1→8 加速比 / 效率 |
|---|---:|---:|---:|---:|---:|
| 950PR armA | 73.610 | 77.498 | 81.503 | 3.799× / **95.0%** | 7.225× / **90.3%** |
| 950PR armB | 64.872 | 68.757 | 72.233 | 3.774× / **94.3%** | 7.185× / **89.8%** |
| H20 armA | 119.895 | 128.475 | 141.541 | 3.733× / **93.3%** | 6.777× / **84.7%** |
| H20 armB_h20_sw | 112.309 | 121.427 | 134.806 | 3.700× / **92.5%** | 6.665× / **83.3%** |
| H20 armB（EGL） | 70.244 | 72.249 | 76.984 | 3.889× / **97.2%** | 7.299× / **91.2%** |

**8 卡这一级两边的差距比 4 卡大**：同一份活、都在 CPU 上渲染时，
950PR 的 1→8 效率是 90.3%，H20 是 84.7%。4 卡上这个差只有 1.7 个百分点，
8 卡上是 5.6 个 —— 所以 armA 的盈亏平衡 x 从 4 卡的 1.658 涨到 8 卡的 1.737（5.5 节），
**950PR 的优势随卡数变大**。

逐阶段看 950PR armA 的涨幅，加速器和主机两侧涨得几乎一样多：

| 阶段 | 1→4 卡 | 1→8 卡 |
|---|---:|---:|
| `rollout/predict` | +6.88% | +10.69% |
| `actor_training` | +6.49% | +10.34% |
| `env_interact_step` | +5.75% | +11.85% |
| `env/bootstrap_step` | +2.29% | +9.28% |
| 加速器阶段合计 | **+6.72%** | **+10.55%** |
| 主机阶段合计 | **+4.92%** | **+11.23%** |

加速器侧的涨幅是 `no_shard` 的 all-reduce 随卡数变贵；主机侧是 8 卡 × 8 env = 64 个
并行 env worker 对 256 线程的压力。两侧量级相同，所以 950PR 的扩展损失没有单一来源。

**这一节纠正了早先的一个结论。**早先报的是"950PR 1→4 卡只涨 1.69%、效率 98.3%"，
那是争用造成的假象：1 卡那批 run 的邻居 CPU 约 33 点、4 卡那批约 19 点，
1 卡被压得更狠，两级之差因此被抹平。安静窗口下的真实扩展损失是 5.28%（armA 1→4 卡）。
**armA 对 armA 现在可以比了，而且方向和 armB 相反：4 卡 950PR 95.0%、H20 93.3%，
8 卡 90.3% 对 84.7%。**同一份活、同样都在 CPU 上渲染时，950PR 的扩展比 H20 好，
而且卡越多差得越开。H20 armB（EGL）那 97.2% 并不推翻这条 ——
它扩展得好是因为 GPU 渲染把主机侧那一大块（扩展损失的来源之一）整个搬走了，
不是同一份活。**H20 的第三条臂把这一点钉死了：**`armB_h20_sw` 开着同样的开关、
但渲染仍在 CPU 上，它的 1→8 效率是 83.3% —— 比 armA 的 84.7% 还低一点，
离 EGL 那条臂的 91.2% 差了 8 个百分点。
所以 H20 那 91.2% 完全来自渲染后端，和开关无关。
补测的两条 srr 臂给出同一幅图（`armB_h20_sw_srr` 的 1→8 是 **83.9%**、
`armB_split_srr` 是 **91.7%**），所以 `skip_reset_renders` 也不动扩展效率 ——
它省掉的是每步固定的一段 reset 渲染，不是随卡数长的那一段。

## 6. FLOPs 与 MFU

### 6.1 分子怎么来的

`rollout.count_flops_calls` 与 `actor.count_flops_micro_batches` 两个挂载点在标定 run 里
打开（计数要为每个被派发的算子付一次 Python 调用，所以绝不能开在计时的 run 上）。
每项都取前两次调用，两次必须完全相等 —— 本轮全部相等，这才支持"测一次乘以循环数"。
标定时关掉 activation checkpointing，否则重算的前向会被数两遍（报的是 MFU 而不是 HFU）。

昇腾的融合 attention 是定制算子、没有自带 flop 公式，未修正的计数会把它算成零 FLOPs，
让用融合算子的平台看起来做的活更少。`flop_counting.py` 为它注册了 `4·B·H·T·S·D`，
`flop_formula_check.py` 断言融合开与关的计数相等。

### 6.2 标定结果

同一份 1 卡配置，每次调用的 FLOPs：

| | rollout predict / 次 | actor train_micro_batch / 次 |
|---|---:|---:|
| H20 armA | 35,316,813,008,896 | 74,547,479,994,368 |
| H20 armB（`enable_fused_prefix`） | **35,316,813,008,896** | 72,336,763,019,264 |
| 950PR armA | **35,316,813,008,896** | 74,348,166,668,288 |
| 950PR 仅融合算子（不开 `skip_masked_images`） | **35,316,813,008,896** | 74,302,018,838,528 |
| 950PR armB（再加 `skip_masked_images`） | 34,207,698,522,112 | 70,779,193,548,800 |

四件事，第三、第四件最重要：

1. **rollout 路径两平台精确相等，而且是逐算子相等**：
   `aten.mm` 30,843,737,210,880、`aten.addmm` 3,324,782,841,856、
   `aten.bmm` 1,139,969,359,872、`aten.convolution` 8,323,596,288，四项在两台机器上
   逐位相同。这是"在 dispatcher 层可移植地计数"这一设计最强的证据 —— 同一组 `aten` 算子，
   落在 CUDA 还是落在昇腾都数出同一个数。
2. actor 路径两平台差 199,313,326,080（**0.267%**），H20 这边多算。逐算子表（计数 run
   现在会把它打出来）把这 0.267% 定位到了单一算子：

   | 算子 | H20 | 950PR | 差 |
   |---|---:|---:|---:|
   | `aten.addmm` | 7,522,542,952,448 | 7,522,542,952,448 | 0 |
   | `aten.bmm` | 5,313,125,154,816 | 5,313,125,154,816 | 0 |
   | `aten.convolution` | 16,647,192,576 | 16,647,192,576 | 0 |
   | **`aten.mm`** | 61,695,164,694,528 | 61,495,851,368,448 | **199,313,326,080** |

   差值恰好等于 16 × 2 × 1485 × 2048 × 2048 —— 每个样本一个无 bias 的 2048×2048 矩阵乘
   作用在 1485 个 token 上，H20 多派发一次。`aten.mm` 而不是 `addmm`，说明它来自反向
   （grad_input 与 grad_weight 都是 `mm`），形状是投影层而不是注意力（`bmm` 两边逐位相同）。
   最可能是第一层投影的 grad_input 在一边被算了、另一边没算。**还没定位到具体模块** ——
   要再深一层得打 `by_module` 的逐模块表。0.267% 不影响任何结论，记为已知缺口。
3. **950PR 的三个融合算子精确保持 rollout FLOPs 不变、只让 actor 变 −0.062%；而
   `skip_masked_images` 砍掉 rollout 3.14%、actor 4.74% 的算力。**
   逐算子表把"融合算子不改算力"这句话变成可检验的：

   | | rollout `aten.bmm` | rollout `npu.npu_fusion_attention` | rollout 合计 |
   |---|---:|---:|---:|
   | 开关全关 | 1,139,969,359,872 | 0 | 35,316,813,008,896 |
   | 融合打开 | 0 | **1,139,969,359,872** | **35,316,813,008,896** |

   **`bmm` 的那一笔整数搬进了融合算子，一位不差** —— 注册的 `4·B·H·T·S·D` 公式在前向上
   是精确的。actor 侧（含反向）则是 `bmm` 少了 2,279,938,719,744、融合算子只记上
   2,233,790,889,984，差 46,147,829,760，即**被替换掉的注意力算力的 2.02%**、整步的 0.062%。
   所以这个缺口在反向里：前向精确，反向差 2%。
   所以 armB 不是"同样的活干得更快"，它确实干得更少 —— armB 对 armA 的 12.51% 里有一部分
   是算法层面的。MFU 的分子必须用各臂自己的计数，照搬会把加速报两遍。
4. **H20 的 `enable_fused_prefix` 也在少算**：rollout 不变（它在 rollout 侧是关的），
   actor 少 2.97%。融合后的 prefix 不走梯度，所以反向少算，这与二期报告里"融合的显存收益
   仅限前向"是同一件事的两面。

把两边合起来看（用实测的每步调用次数加权）：

每步每卡的总算力 = `predict 每次 × 79 + micro batch 每次 × 24`（次数见 6.3）：

| | 每步总算力（TFLOP/卡） | 对自家 armA |
|---|---:|---:|
| H20 armA | 4579.2 | — |
| H20 armB | 4526.1 | −1.16% |
| 950PR armA | 4574.4 | — |
| 950PR armB | 4401.1 | −3.79% |

- **armA 对 armA：两边算力只差 0.10%**，是真正的同一份活，跨平台的 1.629 倍可以直接读。
- **armB 对 armB：950PR 比 H20 少算 2.76%**，所以 1 卡加速器阶段那 2.213 倍折算成同等算力
  （比 FLOPS 而不是比墙上时间）是 **2.152 倍**，4 卡的 2.195 倍折算后是 **2.135 倍**。
  这个折算对调用次数不敏感：在 48–160 次 predict、4–48 个 micro batch 的范围内，
  少算的比例都落在 2.6%–3.1%。

### 6.3 每步被计数的调用次数

把"每次 FLOPs"变成"每步 FLOPs"要乘以每步的调用次数，而这个次数是实测的，不是从 config
推算的 —— 推算是推导，不是测量。做法：把两个计数器设到远高于真实次数（10000），
跑 1 步，数日志行。

| 测法 | rollout predict / 步 / 卡 | actor train_micro_batch / 步 / 卡 |
|---|---|---|
| 1 卡，1 步 | 81 | 24 |
| 1 卡，3 步（逐步） | **81 / 77 / 78** | **24 / 24 / 24** |
| 4 卡，1 步（逐 rank） | 81 / 78 / 78 / 83 | 24 / 24 / 24 / 24 |

**actor 侧是确定的 24**，三步逐步相同，而且对得上配置：每步 8 env × 240 步 ÷ 5 个
action chunk = 384 个样本，micro batch 16，正好 24 个；`global_batch_size: 64` 则对应
6 次优化器步、每次 4 个 micro batch。

**rollout 侧是 77–81，平均 78.7，而原因没定。** 两种解释都成立：

- 真实抖动。240 ÷ 3 = 80，和观测到的量级吻合（说明每次查询只执行 3 个 env 步，
  而不是 chunk 的 5 个），每步差一两次查询来自 episode 边界。
- Ray 在高负载下丢转发的日志行。**"数到的行数"不等于"调用次数"**，而一行一次调用的
  计数方式对丢行没有任何防护 —— 少一次调用和少一行日志在日志里长得一样。

分不开，所以本报告按 **79 ± 2（±2.5%）** 用，并把这个不确定度带进 MFU 的 rollout 分子。
修法现在已经部署：每行带上剩余预算，让日志行构成严格递减序列，丢行就是序列里的一个
缺口，看得见。本轮的计数 run 在部署之前，所以这 77–81 要到下一个计数 run 才能分清。

1. **950PR 的绝对吞吐高 1.84 倍，MFU 却低 17 个百分点。** 它把 2.643 倍的 GEMM 上限只

   **它缺的不是算力。**
2. **整个 step 的 MFU 两边都很低**（27.4% / 16.8%），因为分母里包含 CPU 渲染的时间。

1. **两边的开关都确实提高了加速器 MFU**（H20 55.6 → 65.2、950PR 38.7 → 51.7），
   这是内核优化该有的样子。
2. **950PR 开上自己的内核后，加速器 MFU 51.7%，已经接近 H20 不开优化时的 55.6%** ——
   它把自己那块大得多的上限用得几乎和 H20 用小上限一样好。昇腾侧的优化工作在这个指标上
   是立住的。
3. **整个 step 的 MFU 才是差距真正炸开的地方：46.1% 对 18.4%，差 2.5 倍。**
   H20 的 EGL 把 step 从 CPU 渲染里解放出来，950PR 的 step 仍有 69% 在 CPU 上。
   如果要用一个数来说明"缺图形栈的代价"，就是这一个。
4. **MFU 随卡数单调下降**（950PR armB 51.7 → 48.6 → 46.4），与 5.4 的扩展效率
   94.3% / 89.7% 是同一件事的两种写法：分子不变、分母（时间）变长。
5. **GPU 渲染是拿加速器 MFU 换 step MFU，而且两级卡数上都成立。**
   加速器 MFU 最高的那条臂是 armB_h20_sw 而不是开着 EGL 的：
   1 卡 **67.6% 对 65.2%**、4 卡 **64.1% 对 60.1%** —— 渲染搬上 GPU 之后要和推理抢卡
   （4.1 与 5.1 的最后一列）。但 step MFU 反过来：1 卡 28.9% 对 46.1%、4 卡 26.7% 对 44.8%。
   EGL 让加速器效率低了 2–4 个点，却让整个 step 的效率高了 17–18 个点。
   **这条也解释了为什么只看加速器 MFU 会选错配置**，该看的是 step MFU。

### 6.5 功耗与每步能耗（目前只有 H20 一侧）

每步能耗 = 该卡稳态功耗 × 该格的 `time/step`。

| π₀.₅ 4 卡 armA | 192.4 | 128.475 | 24,714 |
| π₀.₅ 4 卡 armB_h20_sw | 212.3 | 121.427 | 25,776 |
| π₀.₅ 4 卡 armB（EGL） | 274.8 | 72.249 | **19,851** |
| π₀.₅ 8 卡 armA | 187.8 | 141.541 | 26,588 |
| π₀.₅ 8 卡 armB_h20_sw | 204.7 | 134.806 | 27,594 |

| GR00T 8 卡 armB（EGL） | 160.1 | 50.366 | **8,065** |

空闲卡的底噪是 72.7–75.7 W，这张卡的 TDP 是 400 W。
每一行都是 `energy.py` 从该 run 的 `power.csv` 算的（第 11 节）。
1 卡与 4 卡要显式指定承载 run 的卡：那几个 run 的采样里**有一张邻居的卡**
（容器 4 号常驻 123 W，底噪是 73 W），按"高于底噪就算在跑"的启发式会把它算进来。
8 卡那几行八张卡全在跑，没有底噪可比，所以也要显式指定 —— 工具在这两种情况下都会拒绝猜。

**两个杠杆在能耗上的账完全不一样：**

| | 功耗 | 时间 | 每步能耗 |
|---|---:|---:|---:|
| 开关（4 卡 armA → armB_h20_sw） | +10.34% | −5.49% | **+4.30%** |
| 开关（8 卡） | +9.00% | −4.76% | **+3.78%** |
| EGL（8 卡 armB_h20_sw → armB） | +28.19% | −42.89% | **−26.80%** |
| EGL（GR00T 8 卡） | +17.63% | −57.64% | **−50.15%** |

- **H20 的开关买的是时间，不是电。**它让功耗涨得比时间省得多，所以每步能耗反而高 4%。
  要省电就别开它；要省时间才开。
- **EGL 两头都赚。**它把渲染搬上 GPU，功耗涨 28%，但时间省 43%，净省 27% 的能耗；
  GR00T 那一格省一半。所以"渲染放哪"这件事在能耗上和在时间上是同向的，
  而且幅度更大。
- **这张卡从来没吃满过。**8 卡 armA 只到 TDP 的 47.0%，开了 EGL 也只有 65.6% ——
  和 6.4 节的 MFU 是同一件事的两种说法。

**采样器的修复在它自己产出的第一个 run 上就自证了。**950PR 原来的采样器读整表
`npu-smi info`，在争用下会停止回答；逐设备 `-t power` 的修复早就在仓库里，
本轮刻意没部署（10 节第 11 条说明了原因），时间格子发表之后那个理由过期了。
部署后八个 run 的两列同时在采：逐设备的 `power_rt_w` 每次都是满的，
整表的 `power_w` 少 12%–54% —— 正是这一条缺口描述的那个失效，
而两列同时有值时彼此只差半瓦上下。

### 7.2 真实价格

| | 整机月租 | 卡数 | 单卡月租 |
|---|---:|---:|---:|
| H20 96G | 3.5 万 – 4.0 万 | 8 | 4375 – 5000 元 |
| 950PR（暂定，待折扣） | 5.0 万 – 5.5 万 | 16 | 3125 – 3438 元 |

而 armA 有一半以上的时间在主机侧，所以 armA 本来就是整机对比。买的是整机、算的是整机价，
两边口径一致 —— 宿主机 CPU 的差异不需要从结论里剥出来，它是你付的钱的一部分。

### 7.3 结论：π₀.₅ × LIBERO 的九个口径下 950PR 都更便宜

成本比 = x ÷ 盈亏平衡 x，即同样一份活 950PR 要花 H20 的多少倍。

| 卡数 | 口径 | 盈亏平衡 x | 成本比 @ x=0.700 | 省 | 价格区间内 |
|---|---|---:|---:|---:|---|
| 1 | 开关全关，都 OSMesa | 1.629 | 0.430 | **57%** | 0.384 – 0.482 |
| 4 | 开关全关，都 OSMesa | 1.658 | 0.422 | **58%** | 0.377 – 0.474 |
| 8 | 开关全关，都 OSMesa | 1.737 | 0.403 | **60%** | 0.360 – 0.453 |
| 1 | 开关都开，都 OSMesa | 1.707 | 0.410 | **59%** | 0.366 – 0.461 |
| 4 | 开关都开，都 OSMesa | 1.725 | 0.406 | **59%** | 0.362 – 0.456 |
| 8 | 开关都开，都 OSMesa | 1.827 | 0.383 | **62%** | 0.342 – 0.430 |
| 1 | 各平台最优，H20 开 EGL | 1.079 | 0.649 | **35%** | 0.579 – 0.729 |
| 4 | 各平台最优，H20 开 EGL | 1.052 | 0.665 | **33%** | 0.594 – 0.747 |
| 8 | 各平台最优，H20 开 EGL | 1.056 | 0.663 | **34%** | 0.592 – 0.744 |

**渲染后端不再决定结论的方向，只决定幅度 —— 而且连吞吐的方向也不再由它决定。**
渲染都在 CPU 上时 950PR 省 57%–62%；H20 用上 GPU 渲染后 950PR 仍然省 25%–42%，
因为它最贵的价格角落（x = 0.786）也还低于最紧的那个盈亏平衡 x（1.052）。

这个结论在整个报价区间内都成立，而不是只在中位价上成立。最紧的格子是 4 卡 + H20 开 EGL，
那里 950PR 还有 **1.34 倍的余量**（最坏角落）。换成价格说：在那一格上，950PR 要报到
**7.4 万 – 8.4 万/月/16 卡** 才会打平（H20 取 3.5 万 / 4.0 万对应），
而现在的暂定价是 5.0 万 – 5.5 万。折扣谈成什么样都有相当大的空间。

### 7.4 一个会把结论翻过来的前提：整机得填满

上面的单卡成本是整机价除以卡数，这一步成立的条件是**整机的卡都在干活**。
而两边的整机粒度不一样：H20 一台 8 卡，950PR 一台 16 卡 —— 950PR 要达到同样的利用率，
需要一倍宽的作业，或者一倍多的作业把机器填满。

填不满就是在为空卡付钱，而单卡成本按实际用到的卡数摊：

| 950PR 用掉 | 有效单卡成本 | 有效 x | 1 卡 OSMesa | **8 卡 OSMesa** | 1 卡 EGL | 4 卡 EGL | **8 卡 EGL** |
|---|---:|---:|---:|---:|---:|---:|---:|
| 16 / 16 | 3125 – 3438 | 0.625 – 0.786 | 省 57% | 省 **60%** | 省 35% | 省 33% | 省 **34%** |
| 8 / 16 | 6250 – 6875 | 1.250 – 1.571 | 省 14% | 省 **19%** | **贵 30%** | **贵 33%** | **贵 33%** |
| 4 / 16 | 12500 – 13750 | 2.500 – 3.143 | **贵 72%** | **贵 61%** | **贵 160%** | **贵 166%** | **贵 165%** |

（成本比取中位价，省/贵的百分比是对 H20 而言。两个 8 卡列用的都是实测 x ——
OSMesa 1.737（5.5 节）、EGL 1.056（5.6 节），不是从 1/4 卡外推的。）

**8 卡作业正好是最尴尬的那一档**：它填满一台 H20，却只填半台 950PR。在那一档上，
H20 能用 GPU 渲染的话 950PR 贵 **33%**（实测，不再是从 4 卡外推的 29%–33%），
渲染都在 CPU 上的话 950PR 还省 **19%**。4 卡作业更糟。所以这份对比的成本结论有一个部署形态的前提，而不只是一个价格前提：

- **要按 16 卡的粒度投产**（一台机器跑满，或多个作业共享一台），才有 7.3 那一栏的 34%–57%。
- 只跑 8 卡或更窄的作业，又用得上 H20 的 GPU 渲染，那么 950PR 现在的报价不划算。

这一节没有新测量，只是把 7.2 的除法写清楚 —— 但它比 7.3 的任何一个数都更能决定买哪个。

**8 卡这一档原先的数据缺口已经填上一半了，而且方向和当时猜的一致。**
早先只有 950PR 的 8 卡（81.503 / 72.233 s），H20 的容器只有 6 张卡跑不了，
所以上表的 8/16 行只能用 1、4 卡的 x，并且注明"如果 H20 的 8 卡扩展比 950PR 差，
这一行对 950PR 偏保守"。现在 H20 的 8 卡 armA 已经实测：1→8 效率 **84.7%** 对
950PR 的 **90.3%**，确实更差，所以那条保守性是真的 ——
OSMesa 口径在 8/16 这一档从"省 14%"变成"省 19%"。
EGL 口径的 8 卡也实测了（x = 1.056，5.6 节），8/16 这一档是贵 33% ——
和 4 卡那一档的 33% 相同，所以**这个口径上从 1/4 卡外推是准的**，
而 OSMesa 口径上外推偏保守。差别在于 EGL 把主机侧搬走了，而主机侧正是
两台机器 CPU 规格不对称的地方（5.5 与 5.6 节）。
口径三（开关都开、都 OSMesa）的 8 卡现在也实测了（x = 1.827，5.7 节）：
那个口径在 8/16 这一档上 950PR 还省 **23%**，所以这一档的方向完全由渲染后端决定 ——
H20 用得上 EGL 就贵 33%，用不上就省 19%–23%。

## 8. GR00T N1.7 × LIBERO：同一对硬件，相反的结论

前面七节是 π₀.₅。换成 GR00T N1.7、其余一切不动（同一个仿真、同样的弱扩展梯级、
同样的两条臂定义、同样的安静窗口口径），结论会翻过来。这一节单独成节，
因为它说明的不是"再加一个模型的数"，而是**这个对比的结论取决于什么**。

### 8.1 臂比 π₀.₅ 干净，但口径不比 π₀.₅ 干净

GR00T N1.7 没有昇腾融合算子路径（`npu_patches` 在 `gr00t_n1d5` 下，`gr00t_n1d7`
不 import 它）、没有 `skip_masked_images`、也不接受图编译（`base_policy` 对这个策略拒绝）。
所以两个平台剩下的杠杆只有两个：LIBERO 环境的 `skip_reset_renders`（两边都有），
和渲染后端（只有 H20 有）。

- **armA**：无 override，两边都 OSMesa。配置、代码树、权重三者都相同
  （梯级 md5 逐个相同，树 `f5c7f951`，两个 checkpoint 在两台机器上逐字节同样大、
  每个权重分片的首尾兆字节指纹相同），**但两边的 rollout 行为不同 —— 见 8.6，
  那是这一格最大的保留。**
- **armB**：两边都开 `skip_reset_renders`，H20 另外换 EGL。两条臂只差渲染后端。

梯级配置两边 md5 逐个相同（1 卡 `ffa10ebd`、4 卡 `7eb3999b`、8 卡 `f362a30e`）。
H20 的 armB run `gl_renderer` 全部记录为 `NVIDIA H20/PCIe/SSE2`、armA 全部 `llvmpipe`，
新 `run_arm.sh` 的 EGL 硬门在起作用。两边 armA 的 `gl_renderer` 连版本串都相同
（`llvmpipe (LLVM 15.0.7, 256 bits)`），所以 armA 这一格连软件光栅化器都是同一个版本。

### 8.2 吞吐

| `time/step` | 1 卡 armA | 4 卡 armA | 8 卡 armA | 1 卡 armB | 4 卡 armB | 8 卡 armB |
|---|---:|---:|---:|---:|---:|---:|
| H20 | 94.178 ± 1.311 | 108.396 ± 1.594 | 118.903 ± 0.254 | **41.402 ± 0.964** | **46.836 ± 0.565** | **50.366 ± 0.541** |
| 950PR | 69.406 ± 1.273 | 76.409 ± 0.404 | 83.670 ± 1.140 | 59.815 ± 0.838 | 65.375 ± 0.979 | 73.785 ± 0.216 |
| H20 / 950PR | 1.357× | 1.419× | **1.421×** | **0.692×** | **0.716×** | **0.683×** |

三级每臂都是 3 个 run、全部 exit 0，H20 的 8 卡跑在重建后的 8 卡容器上（10 节第 1 条）。
8 卡窗口内 `step_cv` 是 H20 2.0%–3.9%、950PR 1.2%–3.0%，都落在这个模型自己的那一档里
（2.3 节与 8.6 节末）。

**H20 的 EGL 在这一格值 −56% 到 −58%**（1 卡 −56.04%、4 卡 −56.79%、8 卡 −57.64%，随卡数轻微走高），
`env_interact_step` 被砍掉 71%–73%。950PR 的 `skip_reset_renders`
只值 −13.8% / −14.4% / −11.8%（1/4/8 卡）—— 它没有图形栈可搬。

### 8.3 为什么方向和 π₀.₅ 相反

**不是因为 950PR 在这个模型上慢了。**加速器阶段 950PR 照样快：

| 1 卡 armA | H20 | 950PR | H20 / 950PR |
|---|---:|---:|---:|
| `rollout/predict` | 4.458 | 2.631 | 1.694× |
| `actor_training` | 12.259 | 6.819 | 1.798× |
| 加速器阶段合计 | 16.717 | 9.450 | **1.769×** |
| `env_interact_step` | 73.481 | 57.874 | 1.270× |

1.769 倍和 π₀.₅ 的 1.844 倍是同一个量级。**变的是这段占多少：**

| 在 H20 上 | 加速器两项占 step | 主机侧占 step |
|---|---:|---:|
| π₀.₅ 1 卡 armA | 49.2% | 59.2% |
| GR00T 1 卡 armA | **17.8%** | 78.0% |
| GR00T 4 卡 armA | **17.6%** | 78.3% |
| GR00T 8 卡 armA | **17.6%** | 78.4% |

这个占比在三级卡数上是平的，所以上面那条解释不是只在 1 卡成立。

GR00T 每步每卡只有 432.17 TFLOP，是 π₀.₅ 的 1/10.6（6.2 与 8.6 节），
但 step 时间两者相当 —— 省下来的时间全花在 CPU 仿真上。
所以**谁赢取决于仿真占 step 多少，而不是谁的芯片快**：
仿真占一半时（π₀.₅）加速器的 1.8 倍能兑现成端到端优势；
仿真占八成时（GR00T）H20 把那八成搬到 GPU 上就够了。

**但 1.769 倍只是 1 卡的数，它随卡数在掉：**

| armA 加速器阶段合计 | H20 | 950PR | H20 / 950PR |
|---|---:|---:|---:|
| 1 卡 | 16.717 | 9.450 | **1.769×** |
| 4 卡 | 19.081 | 11.645 | 1.639× |
| 8 卡 | 20.953 | 15.864 | **1.321×** |
| `env_interact_step` 1 / 4 / 8 卡 | 73.481 / 84.883 / 93.251 | 57.874 / 62.397 / 65.251 | 1.270× / 1.360× / 1.429× |

**所以 8 卡那一格的 x（1.421）和 4 卡的 1.419 几乎相等，不是"稳定"，是两个相反的趋势正好抵掉：**
加速器侧 950PR 的优势从 1.769 倍掉到 1.321 倍（8.5 节那条 all-reduce），
主机侧 H20 的劣势从 1.270 倍涨到 1.429 倍。换句话说，
**GR00T 这一格的 x 到了 8 卡是靠 H20 的主机侧继续变差撑住的，不是靠 950PR 的芯片。**

### 8.4 MFU：这个负载根本没用到算力

分子是精确的（计数器设到 10000、`max_steps=1`，两条 `left=` 序列都无缺口：
rollout 9999→9978 共 22 行 22 次调用，actor 9999→9968 共 32 行 32 个 micro batch，
每次调用的 FLOPs 在所有调用上完全相同），
分母是 3.2 节那组卡自己的实测峰值。

| 950PR | 1 卡 armA | 1 卡 armB | 4 卡 armA | 4 卡 armB | 8 卡 armA | 8 卡 armB |
|---|---:|---:|---:|---:|---:|---:|
| 加速器阶段 MFU | 12.4% | 12.7% | 10.1% | 10.2% | 7.4% | 7.4% |
| 整个 step MFU | **1.7%** | **2.0%** | **1.5%** | **1.8%** | **1.4%** | **1.6%** |

π₀.₅ 在同一块卡上是 38.7%–51.7%（加速器）与 16.8%–18.4%（step）。
**GR00T × LIBERO 这套配置下，950PR 的算力基本没被用到。**
actor 那一行随卡数从 8.2% 掉到 4.4%，是下一节那条 all-reduce 的另一种写法。

H20 一侧用它自己的分子（19 次 rollout 调用 × 10,381,313,827,840 FLOP
加 32 个 micro batch × 8,352,407,271,936 FLOP，合计 464.52 TFLOP/步/卡，8.6 节）
和它自己那几张卡的实测上限（139.6–140.8 TFLOP/s，3.2 节）：

| H20 | 1 卡 armA | 1 卡 armB | 4 卡 armA | 4 卡 armB |
|---|---:|---:|---:|---:|
| 加速器阶段 MFU | 19.90% | 19.90% | 17.41% | 17.15% |
| 整个 step MFU | **3.53%** | **8.03%** | **3.06%** | **7.09%** |

两条臂的加速器 MFU 在同一级上几乎相同（1 卡 19.90% 对 19.90%），这是该有的样子 ——
GR00T 的两条臂只差 `skip_reset_renders` 和渲染后端，都不碰模型算力，所以分子相同。
**真正要看的是 step 那一行：开 EGL 让它从 3.53% 跳到 8.03%**，
算力一点没多用，只是把 CPU 上那段渲染搬走了。这是"MFU 低不等于芯片慢"最干脆的一个例子。
8 卡没有这一行：这台机器只标定了 4 张卡的上限。

**两列不要横着比。**H20 的分子比 950PR 高 7.5%（8.6 节），而它的分母只有 950PR 的 1/2.64
（139.8 对 369.5 TFLOP/s，3.2 节），所以 H20 的 MFU 看起来高一截，主要是分母小，
不是它更会用卡；再加上两边 rollout 行为本来就不一样（8.6 节），
横着比等于把两个未定的量乘在一起。**各看各的那一列**：
结论在两边是同一句 —— 这个负载在哪块卡上都没把算力用起来。

### 8.5 弱扩展：两边都比 π₀.₅ 差，瓶颈也换了地方

| | 1→4 卡 加速比 / 效率 | 1→8 卡 加速比 / 效率 |
|---|---:|---:|
| 950PR armA | 3.633× / **90.8%** | 6.636× / **83.0%** |
| 950PR armB | 3.660× / **91.5%** | 6.485× / **81.1%** |
| H20 armA | 3.475× / **86.9%** | 6.336× / **79.2%** |
| H20 armB（EGL） | 3.536× / **88.4%** | 6.576× / **82.2%** |

1→4 卡 950PR 在两条臂上都比 H20 扩展得好，和 π₀.₅ 的 armA 对 armA（95.0% 对 93.3%）同方向。
**但 1→8 卡 armB 这一行翻过来了**：H20 的 82.2% 超过 950PR 的 81.1%，
而 armA 仍然是 950PR 更好（83.0% 对 79.2%）。
而且两边都比自己在 π₀.₅ 上差（950PR 95.0% → 90.8% → 83.0%），原因不是渲染。
看逐阶段涨幅 —— 最后一列是同一组卡数下的 H20，正好说明上面那个交叉从哪来：

| 阶段 | 950PR 1→4 卡 | 950PR 1→8 卡 | H20 1→8 卡 |
|---|---:|---:|---:|
| `env_interact_step` | +7.82% | +12.75% | +26.90% |
| `rollout/predict` | +10.87% | +17.86% | +17.74% |
| `sync_weights` | +24.86% | +34.81% | +29.69% |
| `actor_training` | **+28.00%** | **+87.17%** | **+28.10%** |

π₀.₅ 的 `actor_training` 同样从 1 卡到 8 卡只涨 10.47%。
GR00T 的 actor 单卡本来只花 6.8 s（π₀.₅ 是 12.7 s），
所以 `no_shard` 的梯度 all-reduce 在一个小得多的计算上占比大得多。
**这一格的扩展损失主要来自 all-reduce，不是来自仿真** ——
和 78% 的主机占比给人的第一印象相反。

**H20 那一列把这条收窄成了一句硬话：同一项在 H20 上只涨 28.10%，950PR 涨 87.17%，差 3.1 倍。**
两边都是 `no_shard`、都是同一份计算、都从 1 卡到 8 卡，所以这不是
"GR00T 的 actor 本来就不好扩展"，而是 950PR 这一侧的梯度 all-reduce 贵得多 ——
和第 1 节逐条第 5 条"算力富、带宽穷"是同一件事的另一个出口。
反过来主机侧是 H20 更差（+26.90% 对 +12.75%），两件事在 step 上部分对冲（8.3 节），
这也是上面 armB 那一行在 8 卡上交叉的原因。

### 8.6 这一格最大的保留：两边的 rollout 行为不一样

**同样的权重、同样的配置、同样的代码树，两边的任务成功率差 2.3–2.7 倍。**

| GR00T | H20 | 950PR | 倍数 |
|---|---:|---:|---:|
| `env/success_once` armA（1 / 4 / 8 卡） | 0.310 / 0.388 / 0.390 | **0.838 / 0.888 / 0.881** | 2.70× / 2.29× / 2.26× |
| `env/success_once` armB（8 卡，H20 开 EGL） | 0.364 ± 0.004 | **0.868 ± 0.012** | 2.38× |
| `env/num_trajectories` 每卡 armA（1 / 4 / 8 卡） | 4.667 / 4.927 / 4.880 | **7.208 / 7.739 / 7.563** | 1.54× / 1.57× / 1.55× |
| `env/num_trajectories` 每卡 armB（8 卡） | 4.844 | **7.651** | 1.58× |

**8 卡原样复现，而且和卡数无关：**三级的成功率倍数是 2.70 / 2.29 / 2.26，
reset 次数倍数是 1.54 / 1.57 / 1.55。所以这不是扩展造成的假象。

π₀.₅ 不是这样：那边 `num_trajectories` 被配置固定成 8/32/64，两边完全一致，
`success_once` 也只差 0.04–0.05（在 run 间离散之内）。
**GR00T 的 `num_trajectories` 不是固定值**，它随 episode 什么时候结束而变，
所以成功率的差异直接变成了"每步做多少次 reset"的差异。

这件事不是 checkpoint 装错了：两个权重目录在两台机器上**逐字节同样大、文件数相同、
每个分片的首尾兆字节 md5 相同**（`GR00T-N1.7-LIBERO/libero_spatial` 35,707,181,860 字节，
`Cosmos-Reason2-2B` 4,889,681,513 字节）。梯级配置 md5 也逐个相同。
所以剩下的候选是加速器内核的数值差异在闭环里被放大，
或者两台机器的 llvmpipe 渲出的图像不完全一致 —— **还没定位**。

**8 卡的 armB 削掉了后一个候选的一半。**那一格 H20 用 EGL（`NVIDIA H20/PCIe/SSE2`）、
950PR 仍是 OSMesa，而 H20 的成功率是 0.364 ± 0.004，和它自己 OSMesa 下的 0.390 ± 0.030
在离散之内 —— **把整个图形栈换掉，H20 的成功率没有朝 950PR 挪半分。**
所以"H20 这一侧渲得不对"被排除了。还站着的是加速器内核的数值差异，
以及"950PR 侧的 OSMesa 输出才是那个异常"这个方向；
后者要求同一个版本的 llvmpipe（两边 `gl_renderer` 连版本串都相同，8.1 节）
在两套 CPU 上渲出不同的图，可能性更低。
要定下来还是得把两边同一个 episode 的首帧逐像素比一次 —— 这件事没做。

FLOPs 计数给了同一件事的第二个证据：

| GR00T 每卡每步 | H20 | 950PR | H20 / 950PR |
|---|---:|---:|---:|
| rollout 每次调用 | 10,381,313,827,840 | 10,299,326,718,976 | 1.008× |
| rollout 每步调用次数 | 19 | 22 | — |
| actor 每 micro batch | 8,352,407,271,936 | 6,424,546,195,968 | **1.300×** |
| 合计 | 464.52 TFLOP | 432.17 TFLOP | 1.075× |

**actor 侧差 30%。**这和成功率是同一件事：episode 在 H20 上更少结束，
序列更长，每个 micro batch 的算力就更大。π₀.₅ 的同一项跨平台只差 0.267%（10 节第 9 条）。

**这对结论的影响，方向是明确的、幅度是未知的。**950PR 每步多做约 1.54–1.58 倍的 reset，
每次 reset 都要渲一帧，所以它的 step 时间被这件事推高：

- **armA（都 OSMesa）**：950PR 做了更多活还更快，所以 1.357× / 1.419× / 1.421× 这三个 x
  是**保守的**，真实差距只会更大。
- **armB（H20 开 EGL）**：H20 做的活更少，所以 0.692× / 0.716× / 0.683× 这三个 x
  **把 H20 的优势算高了**。32%–44% 的差距不可能全由 reset 次数解释（量级不对），
  所以方向上的反转大概率成立，但**幅度要等这件事定位之后才能定**。

**第三个证人：run 内的离散。** GR00T 的 run 窗口内 `step_cv` 在 950PR 上是 1.2%–6.2%、
在 H20 上是 1.5%–8.0%（8 卡那六个 run 分别是 1.2%–3.0% 与 2.0%–3.9%，在带内），
而同一台机器上的 π₀.₅ × LIBERO 只有 0.2%–2.4% 与 0.3%–1.3%
（2.3 节）—— **两台机器各自独立地高出一档**，而且这正是同一个机制该有的样子：轨迹数不由配置固定，
每步结束多少 episode 就得 reset 多少次、渲多少帧，所以 step 时间本身就在步间抖。
π₀.₅ 的轨迹数被配置钉成 8/32/64，它的 step 就没有这个抖动源。
这让 GR00T 这一格的误差条天生比 π₀.₅ 宽，与跨平台那 2.7 倍的成功率差无关，
但两者是同一个根。

8.4 节两边各有一列，但**没有横向并排的结论** ——
分子差 7.5%、分母差 2.64 倍、两边行为还不一样，横着比会把几个未定的量乘在一起。
各看各的那一列，两边给出的是同一句话：这个负载没把算力用起来。

| 卡数 | 口径 | 盈亏平衡 x | 95% 区间 | 成本比 @ x=0.700 | 价格区间内 |
|---|---|---:|---|---:|---|
| 1 | 都 OSMesa | 1.357 | [1.308, 1.408] | 0.516（省 **48%**） | 0.461 – 0.579 |
| 4 | 都 OSMesa | 1.419 | [1.384, 1.455] | 0.493（省 **51%**） | 0.441 – 0.554 |
| 8 | 都 OSMesa | 1.421 | [1.390, 1.453] | 0.493（省 **51%**） | 0.440 – 0.553 |
| 1 | H20 开 EGL | **0.692** | [0.663, 0.723] | 1.011（贵 **1%**） | 0.903 – 1.136 |
| 4 | H20 开 EGL | **0.716** | [0.695, 0.739] | 0.977（省 **2%**） | 0.872 – 1.097 |
| 8 | H20 开 EGL | **0.683** | [0.670, 0.695] | 1.025（贵 **2%**） | 0.915 – 1.151 |

**三个 EGL 口径的盈亏平衡 x 都整体小于 1**，是本轮唯一三格 950PR 在吞吐上落后的 ——
但这六个数都要带 8.6 节那条保留读：两边的 rollout 行为不同，
armA 的三个 x 是保守的，armB 的三个把 H20 的优势算高了。
而 0.692、0.716 与 0.683 都落在报价区间 0.625–0.786 的中间，所以**成本上两边打平**
（中位价上是 省 2% 到 贵 2%，整个区间是 省 13% 到 贵 15%），往哪边倒要看折扣。
EGL 那一列从 4 卡的 0.716 回落到 8 卡的 0.683，原因在 8.3 节：
950PR 的加速器优势被 all-reduce 吃掉得比 H20 快。

对照 π₀.₅ 的同两个口径：1.629 / 1.658 / 1.737（都 OSMesa）与
1.079 / 1.052 / 1.056（H20 开 EGL），那边每一格 950PR 都省 33%–62%。

**所以选型的结论是一句条件句，不是一个数：**

- 工作负载的仿真能用 GPU 渲染、且仿真占 step 七成以上 → 两边打平，看折扣
- 仿真只能在 CPU 上（没有图形栈、或用 OSMesa 口径） → 950PR 省 48%–60%
- 仿真占比低、算力占比高（π₀.₅ 这类） → 950PR 省 33%–57%，H20 开 EGL 也追不上

而且卡数会把第一条往 H20 那边推一点：GR00T 的 EGL 口径 1/4/8 卡是 贵 1% / 省 2% / 贵 2%，
因为 950PR 的 all-reduce 随卡数变贵得更快（8.5 节）。所以"打平"这一档如果要上规模，
得按 8 卡那一格读，不是按 4 卡。

## 9. ManiSkill × π₀.₅：同一份活 950PR 快一倍，各平台最优时 H20 反超

换仿真器，不换模型。π₀.₅ 在 ManiSkill 上重跑同样的弱扩展梯级、同样的两条臂。
这一格的难处不是能不能跑，而是**梯级怎么定** —— 两个平台在这个仿真器上
做不了同一份活，所以它有两个口径。

### 9.1 为什么这一格有两个口径

ManiSkill 的物理后端可以是 GPU，也可以是 CPU。950PR 只有后者：
`sapien.Device("cuda")` 在那台机器上找不到设备，而仓库本来就带着非 CUDA 的跑法
（`tests/e2e_tests/embodied/maniskill_ppo_openpi_pi05_ascend.yaml` 用
`sim_backend: cpu` 配 `render_backend: "pci:0000:00:00.0"`，
`rlinf/envs/sim/maniskill/utils.py` 的 `allow_pci_render_backend()`
专门保住 `pci:` 这个串不被 ManiSkill 自己的解析切坏）。

CPU 后端在一个进程里无法向量化多个环境，所以**每卡只有 1 个 env**，
每步只产出 16 个样本（`rollout_size = 每卡 env 数 × horizon / num_action_chunks × rollout_epoch
= 1 × 80/5 × 1`），批量必须跟着后端缩。GPU 后端那条梯级是每卡 40 个 env、每卡批量 640。
两者差一个量级，没有哪一组参数能同时满足两边。于是：

| | 梯级 | 每卡 env | 每卡 gbs | micro | 这个口径量的是什么 |
|---|---|---:|---:|---:|---|
| 口径一 | `pi05_maniskill_cpu`，两边都跑 | 1 | 16 | 8 | 严格同一份活，但量的是 CPU 物理 |
| 口径二 | H20 `pi05_maniskill`（GPU 物理） | 40 | 640 | 32 | 各平台最优，两边活不一样 |
| | 950PR 仍是 `pi05_maniskill_cpu` | 1 | 16 | 8 | |

口径一是 ManiSkill 这一格唯一"同一套代码、同一组配置"成立的读法
（生成的配置 md5 两边逐个相同：1 卡 `5bff8401`、4 卡 `c1b1c2e8`），
但它量的不是 ManiSkill 的意义所在。口径二两边做的活差一个量级 ——
**而那个量级差本身就是结论**：每卡 40 个环境对 1 个，正是 GPU 并行仿真买到的东西，
而 950PR 买不到。

`pi05_maniskill_cpu` 把 `sim_backend` 与 `render_backend` 写进了生成的配置本身，
所以每个 run 存档的 `rung.yaml` 能独立说明它跑的是什么。
`skip_reset_renders` 不在这一格的臂里 —— 它只被 LIBERO 的 env 读
（`rlinf/envs/sim/libero/libero_env.py`），对 ManiSkill 没有意义；
四个模型级开关照常适用。

### 9.2 950PR：三级梯级，两条臂，18 个 run 全部 exit 0

| `time/step` | armA | armB（四个 NPU 开关） | 开关收益 |
|---|---:|---:|---:|
| 1 卡 | 11.102 ± 0.325 | **9.771 ± 0.099** | **−11.99%** |
| 4 卡 | 12.840 ± 0.126 | **11.290 ± 0.059** | **−12.07%** |
| 8 卡 | 13.798 ± 0.125 | **12.402 ± 0.038** | **−10.12%** |

开关收益在三级上几乎不变（−12.0%、−12.1%、−10.1%），
比 LIBERO 那一格（1 卡 −38.6%、4 卡 −38.3%）小得多，原因在相位构成：

| armA 1 卡 | 秒 | 占 step |
|---|---:|---:|
| `rollout/predict` | 1.556 | 14.0% |
| `actor_training` | 4.529 | 40.8% |
| 加速器阶段合计 | **6.085** | **54.8%** |
| `env/env_interact_step` | 3.512 | 31.6% |
| `sync_weights` | 1.452 | 13.1% |

加速器占 54.8%（8 卡 55.4%，基本不变），比 LIBERO 的 armA 高
—— 每卡只有 1 个环境，仿真摊到每步的时间就小。
所以这一格是**偏算力**的读法，和 GR00T 那一格（加速器只占 H20 一步的 17.8%）正好相反。

`env/env/bootstrap_step` 在这一格恒为 0：ManiSkill 的 env 不走那条路径。

### 9.3 弱扩展：丢在集合通信上，不在渲染上

| 效率（每卡活量不变，理想是 step 恒定） | 1→4 卡 | 1→8 卡 |
|---|---:|---:|
| armA | 86.5% | 80.5% |
| armB | 86.6% | 78.8% |

1→8 卡那 2.696 秒的增量怎么来的（armA）：

| 相位 | 1 卡 | 8 卡 | 增量 | 占 step 增量 |
|---|---:|---:|---:|---:|
| `actor_training` | 4.529 | 5.799 | +1.270 | 47% |
| `sync_weights` | 1.452 | 2.187 | +0.735 | 27% |
| `generate_rollouts` | 5.116 | 5.804 | +0.688 | 26% |

近四分之三的损失在 actor 的 all-reduce 和权重同步上，
`env_interact_step` 只贡献 +14.6%（3.512 → 4.026）。
这和 GR00T 那一格的签名一样（8.5 节），
和 LIBERO 的 π₀.₅ 不一样 —— 那里 `actor_training` 从 1 卡到 8 卡只涨 10.47%。
每卡 1 个环境时，环境这一侧几乎不随卡数变，剩下的全是通信。

### 9.4 口径二的 1 卡：x = 0.798，差距几乎被报价吃掉

H20 的 GPU 物理梯级（每卡 40 个 env、每卡 gbs 640）1 卡三个 run 已收齐，
`step_cv` 0.6%–0.8%：

| | step (s) | 每卡每步样本 | 每卡吞吐（样本/秒） |
|---|---:|---:|---:|
| H20 `pi05_maniskill_1c`，EGL + GPU 物理 | 311.695 ± 5.089 | 640 | **2.053** |
| 950PR `pi05_maniskill_cpu_1c`，armB | 9.771 ± 0.099 | 16 | **1.638** |
| 950PR 同上，armA | 11.102 ± 0.325 | 16 | 1.441 |

两边每步做的活不一样，所以这一格的 x **不能**用 7.1 节
`(cards × t)` 那个式子，要先按活量归一：

**x = (样本/秒/卡)₉₅₀ₚᵣ ÷ (样本/秒/卡)ₕ₂₀**

样本的单位是 action chunk（`rollout_size = 每卡 env 数 × horizon / num_action_chunks
× rollout_epoch`）。模型、chunk 大小、`num_action_chunks` 两边相同，所以这个单位可比；
不可比的是每个样本背后的仿真量 —— 而那正是口径二要量的东西。

| 口径二，1 卡 | 盈亏平衡 x | 95% 区间 |
|---|---:|---|
| 对 950PR armB（平台最优） | **0.798** | [0.773, 0.822] |
| 对 950PR armA（开关全关） | 0.702 | [0.664, 0.740] |

区间用 7.1 节同一套算法（delta 法，`df = (n_a−1) + (n_b−1) = 4`）。
按报价区间 0.625–0.786 折算，这一格按中心值是 **省 1% 到 省 22%** ——
但 x 几乎正好落在报价上限上（0.798 对 0.786），所以**配上区间下界 0.773
和报价上限，结论会翻成贵 2%**。950PR 的成本优势在这一格基本被吃掉。
和同一个模型在 LIBERO 上的口径二（1 卡 1.079、4 卡 1.052）比掉了约 26%，
方向和 8.3 节那条规律一致 —— ManiSkill 的 GPU 物理把更多的 step 搬到了 H20 的 GPU 上，
而 950PR 连渲染都搬不走，更搬不走物理。

**顺带排除了一件事：ManiSkill 这一格没有 GR00T 那个行为分叉。**
`success_once` 两边落在同一个带里 —— 950PR armA 0.375、armB 0.465 ± 0.048，
H20 0.399 ± 0.037，而 GR00T 那一格是 0.310 对 0.838（差 2.7 倍，8.6 节）。
所以那个分叉是 GR00T 自己 env/rollout 路径上的事，不是这一对硬件的通病。
不过两边的梯级不同（每卡 40 个 env 对 1 个），reset 的统计本来就不一样，
所以这只是一个旁证，不是对照实验 —— 对照实验是口径一，已经跑完（9.6 节）。

这个 x 比 7.1 节那六个弱，因为它跨着两种不同形状的负载：
它回答的是"各平台用自己最合适的方式跑 ManiSkill，谁的钱更划算"，
不回答"同一份活谁更快"。后者是口径一，x 是 2.141 与 1.963（9.6 节）。
区间也比 7.1 节那六格宽（±4.3%），因为 H20 这三个 run 的 run 间离散是 1.66% ——
r1 比 r2/r3 慢 3.0%，它的 `sync_weights` 是 3.2 秒而 r2/r3 是 1.8 秒，像是冷启动的尾巴。

### 9.5 口径二的 4 卡：x = 0.711，报价上半区就翻过来了

4 卡这一级的三个 run 已收齐（run 间离散 1.6%，窗口里 0 个外来占卡采样），
归一化用的是和 1 卡同一套（每卡 640 个样本对 16 个，两级的每卡活量都不变）：

| | step (s) | 每卡每步样本 | 每卡吞吐（样本/秒） |
|---|---:|---:|---:|
| H20 `pi05_maniskill_4c`，EGL + GPU 物理 | 321.206 ± 5.082 | 640 | **1.992** |
| 950PR `pi05_maniskill_cpu_4c`，armB | 11.290 ± 0.059 | 16 | **1.417** |
| 950PR 同上，armA | 12.840 ± 0.126 | 16 | 1.246 |

| 口径二，4 卡 | 盈亏平衡 x | 95% 区间 |
|---|---:|---|
| 对 950PR armB（平台最优） | **0.711** | [0.692, 0.730] |
| 对 950PR armA（开关全关） | 0.625 | [0.607, 0.644] |

**x 从 1 卡的 0.798 掉到 4 卡的 0.711，两个区间（[0.773, 0.822] 与 [0.692, 0.730]）
不重叠**，所以这个口径随卡数走低是可分辨的，不是噪声。
按报价区间 0.625–0.786 折算，这一格是 **省 12% 到 贵 11%**：
1 卡那一格只在配上区间下界时才翻（贵 2%），4 卡是**中心值就翻** ——
报价只要高于 0.711，H20 就更便宜。对 armA 那一行更极端：
x = 0.625 正好等于报价下限，也就是说"两边都把开关全关、都 4 卡"这个读法下，
950PR 最好的情况也只是打平。

掉下来的原因是扩展效率，不是单卡性能：

| 1→4 卡（每卡活量不变，理想是 step 恒定） | 1 卡 | 4 卡 | 效率 |
|---|---:|---:|---:|
| H20 口径二（EGL + GPU 物理） | 311.695 | 321.206 | **97.0%** |
| 950PR armB | 9.771 | 11.290 | 86.6% |
| 950PR armA | 11.102 | 12.840 | 86.5% |

**950PR 在这一格的扩展比 H20 差 10 个百分点以上**，而 9.3 节已经指出它丢在哪里：
近四分之三的损失在 actor 的 all-reduce 和权重同步上，不在仿真上。
H20 那 97.0% 则说明 GPU 并行仿真这条路几乎不随卡数变贵 ——
每卡 40 个环境都在本卡上跑完，卡之间只过梯度。
所以 ManiSkill 和 LIBERO 的卡数趋势相反：LIBERO 上口径二是平的（1.079 / 1.052 / 1.056）、
口径三随卡数涨（1.707 → 1.827），ManiSkill 上口径二随卡数**跌**（0.798 → 0.711）。
按这条趋势，8 卡那一级的 x 还会更低，但 8 卡没排（9.7 节）。

**0.711 这个数落在 GR00T 口径二那三格（0.692 / 0.716 / 0.683，8.7 节）的同一个带里**，
而那两格的成因是同一条：H20 一旦能把 step 里那一大段搬到自己的 GPU 上
（GR00T 是渲染，ManiSkill 是渲染加物理），950PR 没有对应的东西可搬。
π₀.₅ × LIBERO 之所以是另一个方向，是因为那一格的加速器占比高到让芯片本身说话（6.4 节）。

### 9.6 口径一：两边同一份活，x = 2.141 与 1.963

口径一两级都收齐了，六个 run 全部 exit 0，run 间离散 0.4%–0.5%。
这是这一格唯一"同一套代码、同一组配置"成立的读法：两边跑同一个
`pi05_maniskill_cpu` 梯级（配置 md5 逐字节相同，9.1 节），每卡 1 个 env、每步 16 个样本。
**而且两边的光栅化栈逐个版本相同** —— 两个容器里都是
`mesa-vulkan-drivers 23.2.1-1ubuntu3.1~22.04.4`、`libvulkan1 1.3.204.1-2`、
lavapipe ICD `api_version 1.1.255`、`sapien 3.0.1`，
MuJoCo 那一侧的 GL 也都是 `llvmpipe`（LLVM 15.0.7）。
（`run_arm.sh` 的 `gl_renderer` 探针读的是 MuJoCo 的 GL 而不是 SAPIEN 的 Vulkan，
所以 SAPIEN 这一侧是另外按包版本核的，10 节第 3 条。）
所以它用 7.1 节那个 `(卡数 × t)` 的式子直接算，不需要按活量归一。

| | H20（lavapipe + CPU 物理） | 950PR armA | 盈亏平衡 x | 95% 区间 |
|---|---:|---:|---:|---|
| 1 卡 | 23.771 ± 0.116 | **11.102 ± 0.325** | **2.141** | [2.039, 2.243] |
| 4 卡 | 25.204 ± 0.097 | **12.840 ± 0.126** | **1.963** | [1.930, 1.996] |

**这是本报告里最高的两个 x**，比 LIBERO 口径三的 1.707 / 1.725 / 1.827 还高一档。
按报价区间 0.625–0.786 折算是 **省 60% 到省 71%**，按中位价 0.700 是省 64%–67%。

同一对硬件、同一个模型、同一个仿真器，两个口径差 **2.7 倍**：

| ManiSkill × π₀.₅ | 1 卡 | 4 卡 |
|---|---:|---:|
| 口径一（两边同一份活，CPU 物理） | **2.141** | **1.963** |
| 口径二（各平台最优，H20 开 GPU 物理 + EGL） | 0.798 | 0.711 |

这不是矛盾，是两个不同的问题。口径一问"同一份活谁更快"，答案是 950PR 快一倍多；
口径二问"各平台用自己最合适的方式跑，谁的钱更划算"，答案是 H20 ——
因为它能把每卡的环境数从 1 个开到 40 个，而 950PR 开不了（9.1 节）。
**整份报告里没有第二处把"口径决定结论"摆得这么清楚。**

逐阶段看 1 卡：

| 相位 | H20 | 950PR | H20 / 950PR | 占 H20 的 step |
|---|---:|---:|---:|---:|
| `actor_training` | 11.134 | 4.529 | **2.458×** | 46.8% |
| `rollout/predict` | 3.555 | 1.556 | 2.285× | 15.0% |
| `env_interact_step` | 6.604 | 3.512 | 1.880× | 27.8% |
| `sync_weights` | 2.413 | 1.452 | 1.662× | 10.2% |
| 加速器两项合计 | 14.689 | 6.085 | **2.414×** | **61.8%** |

**950PR 在每一个相位上都更快，差距最大的是加速器那两项。**
这一格的加速器占比比 LIBERO 的 armA 高（H20 61.8%、950PR 54.8%，9.2 节），
因为每卡只有 1 个环境，仿真摊到每步的时间就小 ——
所以这是本报告里最偏算力的一个读法，这也解释了为什么它给出最高的 x。
它和 LIBERO 口径一的结构差别只有批量（这一格每卡 gbs 16、micro 8，LIBERO 是 64 和 16），
而 H20 的 `actor_training` 劣势从 LIBERO 的 1.80 倍拉到了这里的 2.46 倍。

扩展方向和口径二一致，只是没那么悬：

| 1→4 卡（每卡活量不变，理想是 step 恒定） | 1 卡 | 4 卡 | 效率 |
|---|---:|---:|---:|
| H20 armA（lavapipe） | 23.771 | 25.204 | **94.3%** |
| 950PR armA | 11.102 | 12.840 | 86.5% |

所以 x 从 2.141 落到 1.963，和口径二那一跌（0.798 → 0.711）同一个来源：
950PR 在 ManiSkill 上的扩展差 8 个百分点，而 9.3 节已经把它定位在
actor 的 all-reduce 和权重同步上，不在仿真上。

一条要说明的不对称：H20 这一侧要把 `VK_ICD_FILENAMES` 指到 lavapipe 才跑得起来
（9.7 节），950PR 不需要，因为它根本没有 GPU 的 Vulkan ICD。
那是一个环境变量而不是配置覆盖，而且它让两边**更像**而不是更不像 ——
两边最后绑到的是同一版 lavapipe。
8 卡这一级只有 950PR 侧（13.798 ± 0.125，9.2 节），H20 侧没排（9.7 节）。

### 9.7 这一格的两个保留

**轨迹数不由配置固定。** 和 GR00T 一样（8.6 节），ManiSkill 的
`num_trajectories` 是跑出来的，不是配出来的：armA 1 卡 1.333 ± 0.144、
armB 1 卡 1.583 ± 0.191（差 18.8%）。所以严格地说，臂与臂之间
每步的 reset 次数不完全一样。方向是明确的：**armB 结束的 episode 更多、
reset 更多，却仍然更快**，所以 −12% 的开关收益是被低估的，不是被高估的。
8 卡上两条臂收敛到同样的 11.0 条轨迹和同样的 0.444 成功率。

**两个口径的 1 卡与 4 卡都有了，8 卡两边都没有。** 口径二的 4 卡原先只有一个可用的 run
（r1 死在 CUDA OOM 上，邻居占了卡 0 的 50 GiB，2.5 节；r3 在 run 边界上让位给了 8 卡那一级），
这两个已经在安静窗口里重跑完（9.5 节）。
口径一在 H20 上则是先死了三次：`pci:0000:00:00.0` 不是真实设备地址，
它是向 SAPIEN 要软件光栅化器的写法，只有被选中的 ICD 是软件 ICD 时才解析得出来。
950PR 没有 GPU ICD，默认就落到 lavapipe，所以那个地址在那边能解析；
H20 有 `/etc/vulkan/icd.d/nvidia_icd.json` 优先，于是解析不到。
**把 `VK_ICD_FILENAMES` 指到 `lvp_icd.x86_64.json` 之后那一级在 H20 上跑通了**，
六个 run 全部 exit 0、渲染器确认是 `llvmpipe`（9.6 节）。
8 卡这一级两个口径都没排：容器按 8 张卡重建之后障碍已经不在（10 节第 1 条），
只是这一段队列里没有 8 卡的梯级，而 950PR 侧的 8 卡早就有了。
所以这一格的 1 卡与 4 卡是四个 x，8 卡是零个。

   各出现一次，每次重试把上一次挪到旁边。所以磁盘上只留下**一次** exit 255 的记录，

   而且是在守门脚本等到的安静窗口里跑的（起跑时整机 CPU 0.03%、8 张卡全空）。
   1/1 不是证明，但和端口那个解释一致 —— 之前五次尝试里，加超时的那两次是一成一败。

   **可是这个 run 还是不能进这一格，原因换了一个。**它的 step 是 94.669，
   但不是"慢一档"：12 步里有 6 步是 80.9–82.3（和 r1/r2 的 80.7–82.0 分毫不差），
   另外 6 步是 91.0 / 92.5 / 94.7 / 122.4 / 124.8 / **237.5**。
   `rollout/predict` 同样分裂：干净步 21.0–22.0（r1/r2 是 20.8–22.2），停顿步 31.4–65.3。
   其余相位都很紧（`env_interact_step` 0.4%、`actor_training` 0.9%、`sync_weights` 0.5%）。

   **而这次不是同机 CPU 争用。**它的整机 CPU 均值 19.4，比 r1/r2 的 25.2 / 24.4 **更低**，
   峰值与 p90 也不区分（50.6 / 40.2 对 51.3 / 43.7 和 55.2 / 41.9），主机内存同样不区分。
   最长那次停顿期间我们自己的进程 CPU 掉到约 5% ——
   **是在等，不是被抢**。日志签名与 r1 逐条相同、计数也相同，这个停顿不留任何痕迹。
   所以这一格按不含它的 **n=4、81.503 ± 0.156** 报，这个 run 移到 `runs_stalled/`，
   停顿的来源**没有定位**。候选是昇腾驱动/运行时这一层的主机级争用，
   那条通道 `host_cpu_pct` 看不到。

   这个候选不是假想。复查这台机器时，**卡 12–15 上正跑着另一个租户的四个
   `VLLMWorker_TP`**，每张卡占 89.4 GB、利用率 25%–27%，而我们这边一个 run 都没有。
   那四张卡就在我们 8 卡那一组里（宿主机 8–15），也就是说
   **8 卡的 run 有一半的卡可能是和别人共享的，而 4 卡那一级（宿主机 8–11）没有这个暴露** ——
   这和"停顿只在 8 卡出现"对得上。同时它说明守门脚本原理上防不住这件事：
   它只查起跑前的状态（起跑时 8 张卡确实全空），租户是跑到一半才进来的。
   要把这件事定下来，得在 run 期间持续采逐卡占用，而不是只在起跑前查一次；
   现在的 `power.csv` 只记我们自己可见的那几列，而且device 列在约 1 分钟后失效
   （第 11 条），看不到邻居。

   这件事反过来补上了方法里的一个洞：`aggregate.py` 原来只看 run 间离散，
   会把这个 run 当正常数平均进去。现在它还报窗口内的 `step_cv` 并拒绝越线的 run
   （2.3 节），全部历史 run 已回查，没有别的越线者。

   **重试一那个成功的 run 又落在有争用的窗口里，所以它也不能进安静窗口那一格。**
   它的整机 CPU 均值是 31.5，而 8 卡自己那份约 25.3（2.5 节）——
   多出来约 6 个百分点是邻居（事后在宿主机上看到一个 vLLM 任务，4 个 worker 各约 56%）。
   step 是 87.333，比同格四个安静 run（81.334–81.705）慢 **7.2%**。
   把它算进去会让这一格变成 82.669 ± 2.611（3.2%），正是本轮一直在清掉的那种混窗口口径，
   所以它移到了 `runs_contended/`，这一格按不含它的 n=4、81.503 ± 0.156 报。
   **它反而成了 2.5 节那套争用模型的一次事前验证**：同样的卡、同样的代码树、同样的臂，
   隔了 8 小时，邻居多占 6 个 CPU 百分点就慢 7.0%。
   2.5 节的模型是回头排序现有 run 得出的，这一条是先有模型再撞上的。
8. **两台宿主机的 CPU 规格不对称**（256 线程 EPYC 对 180 线程 Xeon）。
   armA 有 59%–63% 的时间在主机侧，所以 armA 的数字是整机对比而不是加速器对比。
   这不算误差 —— 报价是整机价（7.2 节），但引用 armA 的数字时要知道它包含什么。
9. **两个 FLOPs 计数缺口都已定位到算子，但都没定位到模块。**
   跨平台的 0.267% 全在 actor 的 `aten.mm` 上，是每样本一个 (1485×2048)×(2048×2048)
   的无 bias 矩阵乘，H20 多派发一次（见 6.2）。融合算子的 −0.062% 在反向里：前向逐位精确，
   反向比被替换的 `bmm` 少 2.02%。再往下要打 `by_module` 的逐模块表。两者都不影响结论。
10. **rollout 每步的调用次数是 77–81，分不清是真实抖动还是 Ray 丢日志行**（见 6.3），
   所以 MFU 的 rollout 分量带 ±2.5%。actor 侧的 24 是确定的。
   带剩余预算的日志行已经部署，下一个计数 run 就能分辨。
11. **功耗：两边都有了，1 卡与 4 卡（6.5 节）。8 卡只有 H20 一侧。**
    这一条原来写的是"两边都没有功耗数据"，**那是错的** ——
    H20 走 `nvidia-smi --query-gpu=power.draw`，每一个已发表的 run 的 `power_w` 列都是满的，
    只是从来没有人去算。算出来的结论：950PR 每做同样一份活多耗 15%–175% 的电
    （八格全部如此），但按中位租金加 0.7 元/kWh 折算只值 1.3–2.7 个百分点；
    H20 自己的开关买时间不买电（每步能耗 +4%），EGL 两头都赚（−27%，GR00T −50%）。
    **剩下的缺口是 950PR 的 8 卡功耗没测**（那一级要协调整机，而邻居占着一半卡位），
    以及每格只有 1 个 run、没有跨 run 离散。
    950PR 这一侧的采样器读整表 `npu-smi info`，在争用下约一分钟后就拿不到可解析内容；
    逐设备 `-t power` 的修复一直在仓库里、刻意没部署，因为本轮刚确认同机 CPU 争用是
    一阶误差项（2.5 节），换采样器会动到被测路径上的采样开销。
    **时间格子发表之后这个理由过期了**，修复已部署（旧版留作
    `harness/sample_power.py.pretimecells`，重测时间格子要换回去），
    功耗轮正在 1 卡与 4 卡上跑 π₀.₅ 与 GR00T 的两条臂。
    那一批的 run 名是 `pwr950_*`、臂名带 `_pwr` 后缀，**它们的 step 时间带着新采样器的开销，
    不能进任何时间格子**；跨平台的每步能耗用它们的功耗配已发表的 step 时间算。
    采样间隔调到 15 秒（原来 5 秒），因为修复后每卡每次采样都要调一次 `npu-smi`，
    而那个工具持全局锁、邻居租户也在查它。
12. **rollout 图编译没有日志行**，开关指纹覆盖不到它。
    这一条本轮变得更该修：既然图编译值到 step 的 5.6%–10.8%（4.1 节末），
    "它这一次到底生效了没有"就只能靠时间差反推，没有一行日志作证。
13. **`skip_reset_renders` 的不对称：三级卡数都已补测，这一条关掉。**
    它只开在 950PR 的 armB 上，H20 的 π₀.₅ 三条臂都没开，而这是 LIBERO env 的开关、
    两个平台都有（GR00T 的 armB 两边都开着它）。
    **补测的结论（5.7 节）：口径三 1.731 / 1.766 / 1.866 → 1.707 / 1.725 / 1.827，
    口径二 1.083 / 1.051 / 1.066 → 1.079 / 1.052 / 1.056（1 / 4 / 8 卡）。**
    那个开关在 OSMesa 下砍掉 13%–17% 的 `bootstrap_step`、在 EGL 下只有 1%–4%，
    因为重置渲染本来就在 GPU 上。
    所以此前那个"最紧的 4 卡 EGL 会贴到 1"的担心**解除了**：
    补测后它是 1.052 [1.037, 1.067]，下界仍在 1 以上。
    **六格现在全部是实测，没有一格靠外推。**8 卡那一格的两个 run 被邻居占卡打断过，
    重跑后是 131.972 ± 0.600（n=3，`step_cv` 0.5%–0.7%），x = 1.827（5.7 节末）。
